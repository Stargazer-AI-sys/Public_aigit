# 신규 개발 프로젝트 요구사항 정의서 — 사용자 작성 양식

> 양식 버전: 0.1 | 작성일: 2026-10-15
> 용도: 사용자가 아이디어의 목적·가치·범위를 정의하고, AI가 이를 바탕으로 구체적인 기획과 설계를 진행하기 위한 입력 문서
> 상태: 미작성 양식. 아래 예시는 설명용이며 프로젝트의 확정 요구사항이 아니다.

## 작성 방법

- 각 질문의 **답변**을 본인의 말로 짧게 작성한다. 기술 용어를 사용할 필요는 없다.
- 우선 1~4번과 10번을 작성하면 초기 기획을 시작할 수 있다. 나머지는 아는 범위에서 작성한다.
- 아직 결정하지 못한 항목에는 `미정 — AI 제안 요청`, 필요 없는 항목에는 `해당 없음`이라고 적는다. 모든 칸을 채우기 위해 결정을 억지로 만들지 않는다.
- 기능은 구현 방법보다 **사용자가 무엇을 할 수 있어야 하는지**로 적는다. 필드명·데이터베이스·화면 배치·프로그래밍 언어는 원하는 조건이 있을 때만 적는다.
- `반드시 지킬 조건`과 `선호하지만 조정 가능한 내용`을 구분한다. AI의 제안은 사용자가 확정한 요구사항과 구분한다.
- 이 문서 전달은 기획의 입력이며, 파일 수정·유료 서비스 사용·외부 반영·Git 실행 권한은 별도 요청과 해당 프로젝트 규칙을 따른다.

## AI에게 맡길 기획·설계와 협업 기준

이 절은 작성한 요구사항을 AI가 활용하는 방법이다. 다른 프로젝트의 실행 권한이나 기존 규칙을 변경하지 않는다.

1. **먼저 목적과 범위를 정리한다.** 사용자 답변에서 목표·핵심 기능·부가 기능·제외 범위·성공 기준을 추려 짧게 정리한다. 답변 간 충돌이 있으면 그 영향과 추천안을 설명한다.
2. **세부 기획은 AI가 맡는다.** 사용 흐름, 상세 기능, 화면, 데이터 구조·스키마, 기술 선택, 오류 처리, 개발 단계와 검증 방법을 목적에 맞게 제안한다. 기술적 판단과 사실 확인을 사용자에게 떠넘기지 않는다.
3. **결과 예시로 먼저 설명한다.** 가능한 경우 대표 입력과 읽기 쉬운 결과 예시를 제시한다. 사용자가 원하는 가치가 드러나는지 확인하고 이를 설계에 연결한다. 필드명·자료형부터 하나씩 묻지 않는다.
4. **질문 전에 기존 답변과 자료를 확인한다.** 이미 결정한 사항은 반복해서 묻지 않는다. 미정 항목을 모두 즉시 질문하지 않고, 현재 단계에 필요한 것만 다룬다.
5. **쉽게 바꿀 수 있는 세부 선택은 추천안으로 진행한다.** 기존 조건에 맞는 단순한 방식을 우선하고, 중요한 가정은 짧게 표시한다. 가정을 사용자 확정 요구사항으로 기록하지 않는다.
6. **주요 결정만 묶어서 질문한다.** 목적·핵심 범위·필수 조건의 변경, 비용 부담, 자료 손실·외부 공개, 되돌리기 어려운 선택은 필요한 시점에 확인한다. 각 질문에는 추천안과 사용자 관점의 영향을 함께 제시한다. 별도 권한이 필요한 실행은 승인을 기다린다.
7. **부가 기능과 확장 때문에 첫 버전을 키우지 않는다.** 핵심 기능에 필요한 범위부터 제안한다. 확장 항목은 향후 변경의 부담을 줄일 정도로 고려하고, 선행 구현이 필요하다면 이유와 작업 증가를 설명한다.
8. **요구사항·제안·구현·검증 상태를 구분한다.** 사용자 확정 사항, AI 추천안, 미확정 사항을 구분하고, 설계가 있다는 이유로 개발이나 검증이 끝났다고 표현하지 않는다. 이 양식을 모든 프로젝트의 확정 기능 목록으로 취급하지 않는다.

### AI의 첫 기획 제안에 포함할 내용

- 이해한 목적·사용자·가치와 첫 버전의 범위
- 대표 사용 흐름과 결과 예시
- 핵심 기능·부가 기능·제외 범위의 구분
- 추천하는 구현 방향·진행 순서와 중요한 가정
- 첫 버전의 완료 확인 방법
- 지금 사용자 결정이 꼭 필요한 사항만 모은 질문. 없으면 질문 없이 제안을 마무리한다.
