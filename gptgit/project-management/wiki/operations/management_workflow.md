# 프로젝트 관리 워크플로

이 페이지는 project-management에서 현재 적용하는 일반 관리·기획·검토·인계 흐름을 설명한다. 개별 프로젝트의 상세 규칙과 실행 상태를 대신하지 않는다. 파일 수정, 외부 실행, 비용이 발생하는 작업, 사용자에게 귀속되는 결정은 루트 [AGENTS.md](../../AGENTS.md)와 대상 프로젝트의 최신 규칙에 따른다. 관리 프로젝트의 목적과 현재 범위는 [README](../../README.md), 분류 기준은 [wiki 공통 기준](../AGENTS.md)을 따른다.

~~~mermaid
flowchart TD
    U[사용자 목표와 제약] --> M[마스터가 요청·규칙·현재 상태 확인]
    M --> P[대표 결과와 추천 계획 제시]
    P --> Q{사용자 결정이 필요한가?}
    Q -- 예 --> U
    Q -- 아니오 또는 승인됨 --> A{승인된 실행 작업인가?}
    A -- 아니오 --> R[분석·조언 결과 보고]
    A -- 예 --> H[담당·범위·입출력·완료 기준 정리]
    H --> D[담당 위임 시 herdr pane 제어·결과 회수]
    D --> V[요청 범위 검증·필요한 독립 검토]
    V --> F[근거·미확인·다음 행동 보고]
~~~

## 관리 요청에서 첫 제안까지

먼저 요청의 목적, 관리 대상, 적용 범위와 완료 기준을 확인한다. 대상이 개별 프로젝트라면 그 프로젝트의 최신 README·AGENTS와 필요한 원본을 기준으로 삼는다. 전체 자료를 훑거나 과거 대화만으로 현재 상태를 확정하지 않는다. 최신 진입점과 조회 원칙은 [루트 AGENTS의 작업 시작 기준](../../AGENTS.md#작업-시작과-조회-범위)에 있다.

초기 기획에는 사용자가 평가할 수 있는 대표 결과, 첫 버전의 범위, 핵심·부가·제외 항목, 추천 방향, 중요한 가정과 결정이 필요한 질문을 포함한다. 작성 양식은 입력을 돕는 빈 양식이며, 미작성 항목은 AI가 확인 가능한 자료로 보완하거나 미정으로 남길 수 있다. 기획 방법의 세부 기준은 루트 AGENTS가 연결하는 공유 project-planning 원본을 따른다. 양식의 목적과 사용 조건은 [요구사항 양식](../features/신규_개발_프로젝트_요구사항_작성양식.md)에 설명되어 있다.

가역적인 세부 설계는 기존 제약 안에서 추천할 수 있다. 목적·핵심 범위·필수 조건, 비용, 자료 손실·외부 공개 또는 되돌리기 어려운 선택은 추천안과 영향을 설명하고 사용자 결정을 반영한다. 제안, 사용자 확정, 미정, 보류를 구분한다. 양식 제출이나 기획 문서 작성만으로 실행·파일 반영·외부 작업 권한이 생기지 않는다. 실행 권한의 기준은 [파일 조회와 반영 요청](../../AGENTS.md#파일-조회와-반영-요청)이다.

## 승인된 실행과 담당 분담

실행이 승인된 뒤에는 목적, Task 산출물, 담당, 입력·출력, 파일 소유권, 필수 규칙, 완료·검토·인계 조건을 필요한 만큼 정리한다. 독립적인 조회는 병렬로 진행할 수 있지만, 같은 파일을 동시에 수정하지 않도록 담당과 순서를 구분한다. 검토 담당은 제작 원본을 읽기 전용으로 확인하고 재현 가능한 문제·근거·영향을 반환한다. 최종 통합과 완료 판정은 마스터가 원본·증거를 대조해 수행한다.

요구사항 정리 이후 승인된 실행·제작·검토를 맡길 때는 project-management의 현행 기본으로 herdr pane 제어를 사용한다. 마스터가 pane과 담당을 확인·준비하고, 필요한 작업 정보만 전달하며, 진행 확인·응답 회수·통합을 맡는다. 내장 서브에이전트로 임의 대체하지 않는다. herdr를 사용할 수 없으면 원인과 대안을 설명하고 방식 변경을 확인한다. 단순 질의, 마스터의 직접 판단·통합·간단한 수정마다 pane을 새로 만들지는 않는다. 세부 범위는 [루트 AGENTS](../../AGENTS.md#공통-스킬절차)와 [delegation-reporting](../../skills/delegation-reporting/SKILL.md)을 따른다.

이 위임 방식은 승인된 Task를 수행하는 방법이며, 자동화 운영 전체를 재개하는 허가가 아니다. 비용·외부 서비스·개별 프로젝트 수정·Git은 각기 기존 권한과 요청 범위에 따른다. 실제로 연결하지 않은 담당·모델·도구는 실행한 것으로 기록하지 않는다.

## 검토, 인계와 완료 보고

검증은 요청 범위에 필요한 원본 대조, 실행 결과와 증거 확인, 영향 범위의 검사로 정한다. 구현 완료, 실제 적용, 동작 확인, 독립 검토와 사용자 환경에서만 가능한 확인을 서로 구분한다. 독립 QA가 필요한 경우 별도 실행 증거를 요구하며, 다른 담당의 동의만으로 시험을 대신하지 않는다. 파일을 고쳤다는 사실만으로 정상 동작이나 전체 완료를 선언하지 않는다.

재개 시에는 공식 최신 인계와 이번 요청, 관련 규칙·설계·결정 원본을 대조한다. 개별 프로젝트의 상태는 해당 프로젝트 기록에서 확인한다. [관리 작업기록](../../docs/04_records/management_log.md)은 이 관리 프로젝트의 인계 원본이며, 현재 기록된 8개 후속 시험의 실행 대상은 project-prototype이다. 이를 project-management에서 이미 실행한 것으로 간주하지 않는다.

완료 보고에는 실제 변경, 근거와 수행한 검증, 검사 제외·미확인 범위, 남은 결정과 다음 행동을 구분해 적는다. 실행하지 않은 작업이나 검증은 완료로 쓰지 않는다. 결과 설명과 추가 문서 기록은 요청 범위를 따르며, Git은 별도의 명시 요청이 있어야 수행한다.

## 자동화·문서 점검 자료의 경계

일반 관리와 기획·인계는 이 페이지와 루트 AGENTS의 현행 기준을 따른다. 이전 자동화 단계·역할·process_debug On/Off 운영은 현행 작업 지시가 아니다. 자동화 설계는 [과거 자동화 워크플로](../architecture/automation_workflow.md), 종료된 process_debug 절차는 [raw의 보관 원본](../../raw/skills/process-debug/SKILL.md)에서 당시 맥락으로만 확인한다. 예약 문서 점검은 수동 검증 뒤 추후 검토한다는 과거 제안이다. 실제 예약 생성 여부는 이번 작업에서 확인하지 않았다. 관련 도구는 raw에 보존되어 있으며 현재 실행 기능으로 안내하지 않는다. 상세 범위와 한계는 [문서 점검 기능](../features/document_checks.md)과 [과거 문서 점검 운영 기록](historical_document_checks.md)을 따른다.
