# Codex 관리 워크플로

> 버전: 0.13 | 최종 수정: 2026-10-28
> 적용: 이 관리 프로젝트의 기획·실행·검토·인계. 개별 프로젝트에는 해당 규칙과 요청 범위를 먼저 확인한다.

## 1. 기본 흐름

사용자 요구사항 → AI의 결과 예시·추천안 → 필요한 주요 결정 → 요청 범위 실행 → 관련 검증·필요 시 독립 검토 → 완료 보고.

이는 일반 관리·조언 요청의 흐름이다. 승인된 자동화 프로젝트는 [자동화 워크플로](automation_workflow.md)의 요구사항 → 기획 → 제작·실행 → 독립 QA → 문서화와 단계별 통과 기준을 적용한다. 실행 상태·증거·재시도·문서 책임은 그 문서를 원본으로 삼는다.

- 질문과 권한의 기준은 [AGENTS.md](../../AGENTS.md)의 「질문·작업 완료 기준」 및 「파일 조회와 반영 요청」이 기준이다.
- 사용자는 목적·가치·핵심 범위·중요한 제약을 정한다. [요구사항 양식](../01_requirements/신규_개발_프로젝트_요구사항_작성양식.md)에 아는 범위만 작성하면 된다.
- AI는 상세 기능·데이터 구조·기술·진행 순서·검증 방법을 제안한다. 쉽게 바꿀 수 있는 선택 때문에 사용자에게 반복 질문하지 않는다.
- 스킬은 재사용 절차이며 실행 권한을 추가하지 않는다. 논의 요청은 채팅 결과로, 파일 반영 요청은 지정된 원본 변경으로 마무리한다.

## 2. 초기 기획

**입력:** 아이디어 또는 작성한 요구사항, 기존 제약·참고 자료.

**출력:** 목적과 첫 버전의 범위, 대표 사용 흐름·결과 예시, 핵심/부가/제외 기능, 추천 구현 방향·검증 방법, 중요한 가정과 필요한 질문.

- `project-planning` 스킬을 사용한다. 요구사항 양식을 다 채우지 않았어도 확인 가능한 부분부터 기획한다.
- 사용자가 결과의 유용성을 평가할 수 있게 설명하고, 필드명·자료형·분류 이름을 하나씩 결정하게 하지 않는다.
- 프로젝트의 기존 요구사항·스키마가 있으면 재사용을 검토한다. 별도 요청 없이 구조를 전면 교체하거나 신규 설계를 확정하지 않는다.
- 승인된 자동화는 요구사항·기획 단계부터 Task별 산출물·담당 새 세션·입출력·완료·검토·인계 조건을 기존 실행계획에 설계한다. 세션 전환과 맥락 전달은 [자동화 워크플로](automation_workflow.md) 2.1절을 따른다.

## 3. 실행과 검토의 분담

독립적인 작업이 있고 사용자가 에이전트 사용을 요청했거나 적용 지침이 허용한 경우에만 분담한다. 소규모 수정은 한 에이전트로 처리할 수 있다. 이 문서 자체는 향후 모든 작업의 에이전트 생성 요청이 아니다.

아래는 일반적인 실행·검토 분담 기준이다. 자동화 프로젝트의 GPT·Claude·Hermes 역할과 별도 세션·교차 검증 조건은 [역할 기준](../00_rules/roles.md)을 따른다. 실제 연결되지 않은 역할은 미실행으로 기록한다.

| 역할 | 입력·책임 | 출력·인계 조건 |
| --- | --- | --- |
| 주 에이전트 | 요청·규칙·최신 상태에서 범위와 완료 기준 결정, 결과 통합 | 작업 대상·금지 범위·완료 기준을 담당자에게 전달. 최종 결과와 남은 결정 보고 |
| 실행 담당 | 지정된 파일·기능, 기존 구현, 완료 기준 | 변경 내용·관련 검증·미검증 범위. 검토 가능한 결과를 주 에이전트에 전달 |
| 검토 담당 | 요구사항과 결과·원본·검증 증거. 기본은 읽기 전용 | 재현 가능한 문제·근거·영향, 확인하지 못한 부분. 직접 수정 대신 주 에이전트에 반환 |

- 목표·확정 결정·필요한 원본 절·금지·보류·Task 명세 버전만 선별해 넘긴다. 독립적인 조사만 병렬로 진행하고, 수정은 담당 파일과 순서를 정해 동일 파일 쓰기 충돌을 금지한다. worktree만으로 외부 서비스·공용 데이터베이스까지 분리되지는 않는다.
- 검토 담당에게 이전 결론을 그대로 따르도록 요구하지 않는다. 다른 에이전트의 동의는 검증 증거를 대신하지 않는다.
- 충돌 시 주 에이전트가 사용자 목표·원본·재현 결과로 판단한다. 주요 방침 변경이 필요하면 추천안과 영향을 묶어 사용자에게 확인한다.
- 관리 채팅의 검토 요청으로 개별 프로젝트 소스를 수정하지 않는다. 실제 수정·유료 호출·Git 작업은 각각 허용된 범위에서만 수행한다.

### 문서 점검 확장 작업의 검토·종료 기준

- 구현 요청을 받으면 5절의 범위·완료 기준에 따라 구현 → 관련 검사 → 필요한 수정 → 영향받는 검사 재실행까지 이어간다. 별도 검토 에이전트는 최초 도구 구현 점검이나 영향이 큰 변경에서 필요하고 허용된 경우 활용하며, 가이드 수정 때마다 필수화하지 않는다. 이번 기준의 문서 반영만으로 도구 구현이나 별도 에이전트 생성을 실행하지 않는다.
- 독립 검토를 수행하면 결과·원본·실행 증거를 대조해 누락·오탐·기존 기능 영향·원본 무변경 여부를 확인한다. 주 에이전트가 재현과 근거를 확인해 필수 수정 사항을 정리한다.
- 관련 검사가 통과하고 검토에서 확인된 필수 문제가 해결되면 완료한다. 검토 의견이 있었다는 이유만으로 이미 통과한 전체 검사를 계속 반복하지 않는다.
- 같은 문제가 반복되어 진전이 없거나 요청 범위 밖 변경·새 권한·사용자 결정이 필요하면 해당 부분의 원인·시도 결과·남은 문제·추천 행동을 보고한다. 해결되지 않은 필수 문제가 있으면 완료로 표시하지 않는다.

## 4. 인계 점검

공통 재개·PC 이동·실행 분기·인계 항목은 [공통 작업 흐름](../../../docs/common_workflow.md)의 2절·4절을 따른다. 이 관리 프로젝트는 공식 작업기록의 최신 인계에서 관리 다음 작업을 확인하고, 개별 프로젝트를 검토할 때는 해당 프로젝트의 원본을 확인한다. 관리 요약으로 개별 상태를 대체하지 않는다.

복원은 최신 작업기록 → 관련 결정·설계 원본 대조 → 현재 미저장 대화 반영 순서로 수행하고 결정 완료·미구현·미검증·미정·보류를 구분한다. 제목·색인에서 필요한 범위만 점진적으로 조회한다. 승인된 자동화에서 작업이 예상보다 커지면 알림 → 기존 공식 기록 인계 → 새 세션 → 마스터 종합보고를 따른다. 세션 분할 자체에는 재승인을 요구하지 않으며 주요 변경 승인 기준은 유지한다. 상세 기준은 자동화 워크플로 2.1·2.2절을 따른다.

process_debug On/Off의 응답 표시·기본 증거 유지·사용 규모 추정 한계는 자동화 워크플로 4.1절을 따른다. 도구의 로컬 검사 통과와 실제 새 세션 전달·자동 관찰·프로토타입 완주 검증을 구분한다.

## 5. 수동 문서 점검

### 5.1 현재 구현과 실행

PowerShell 7에서 이 프로젝트 폴더를 작업 위치로 지정한 뒤 실행한다. Codex의 현재 PowerShell 7 실행 환경에서 검증하며, Windows 기본 PowerShell 5.1은 지원 대상에 포함하지 않는다.

개발·실행 명령과 설정은 **프로젝트 루트를 기준으로 상대경로를 우선**한다. 아래 예시를 실행하기 전에 현재 폴더와 PowerShell 7 사용 여부를 확인한다. 실행기는 PATH에서 찾고, 스크립트와 대상은 상대경로로 지정한다.

상대경로 실행이 실패하면 오류로 기록하고 현재 폴더, 파일 존재 여부, 경로 표기·인용, 실행기 검색 경로, PowerShell 버전·실행 정책을 확인하여 원인을 해결한 뒤 같은 상대경로 방식으로 재검증한다. 절대경로 지정이나 다른 폴더로의 변경을 오류 우회책으로 삼지 않는다. 잘못된 작업 위치는 문서에 정한 프로젝트 루트로 바로잡는다.

권한 부족이 원인이면 대상·필요 권한·목적을 설명하고 사용자에게 권한을 요청한다. 임시폴더 변경이나 실행 정책 완화로 권한 오류를 우회하지 않는다. 코드 내부의 경로 탈출 방지용 정규화와 운영체제 연동에 필요한 경로 계산은 사용자별 절대경로를 명령·설정에 고정하는 것과 구분한다.

```powershell
& .\tools\check_project_docs.ps1
```

- 기본 대상은 이 프로젝트의 README, AGENTS, 요구사항 양식, 이 워크플로다. 링크 대상은 존재 여부만 확인하고 재귀 탐색하지 않는다.
- 다른 파일은 명시적으로 지정할 수 있다. 전체 프로젝트를 자동 스캔하지 않는다.

수정한 HTML 가이드만 검사할 때는 다음처럼 지정한다.

```powershell
& .\tools\check_project_docs.ps1 -Files @('guide_docs/공통_가이드_스킬_사용_및_설치_가이드.html')
```

다른 프로젝트는 루트와 파일을 함께 지정한다. Markdown과 HTML을 같은 목록에 넣어도 된다.

```powershell
& .\tools\check_project_docs.ps1 -ProjectRoot '대상 프로젝트의 실제 경로' -Files @('README.md', 'AGENTS.md')
```

**2026-10-15 당시 Stargazer PC에서 사용자가 통과를 확인한 실행 예시**는 다음과 같다. 현재 폴더와 무관하게 실행하며, 다른 PC에서는 실제 프로젝트 위치와 사용 가능한 PowerShell 7 경로를 먼저 확인해 바꾼다. Codex 번들 실행기는 앱 환경에 따라 경로가 달라질 수 있다.

```powershell
$projectRoot = "C:\Users\Stargazer\OneDrive\Desktop\aigit\gptgit\project-management"
$powerShell7 = "$env:USERPROFILE\.cache\codex-runtimes\codex-primary-runtime\dependencies\native\powershell\pwsh.exe"
$checkerPath = Join-Path $projectRoot "tools\check_project_docs.ps1"
$guidePath = Join-Path $projectRoot "guide_docs\공통_가이드_스킬_사용_및_설치_가이드.html"
& $powerShell7 -NoProfile -File $checkerPath -ProjectRoot $projectRoot -Files $guidePath
```

- 출력은 JSON이며 원본·보고서 파일을 저장하거나 Git·네트워크·유료 API를 실행하지 않는다. 종료 코드 0은 검사한 항목에서 문제 없음, 1은 누락·읽기·링크 문제 발견, 2는 실행 조건 오류다.
- 실행 정책 때문에 스크립트 실행 자체가 차단되면 위 종료 코드에 도달하지 못한다. 정책을 자동 변경하거나 우회하지 않으며, 허용된 PowerShell 7 환경에서 실행할 수 있는지 확인한다.
- UTF-8 읽기, 상대 Markdown·HTML 링크의 파일·폴더 존재, 같은 HTML 안의 목차 연결·중복 ID를 확인한다. Markdown 코드 블록·인라인 코드와 HTML 주석·코드 예시 속 링크 문자열은 제외한다. 내용·구현·사실성·원격 최신 상태를 검증하지 않는다.
- Markdown은 일반적인 인라인 링크만 지원한다. 참조형 링크·따옴표 제목·복잡한 괄호 문법은 지원하지 않는다. HTML은 정적인 `a`·`area`·`link`의 `href`와 명시적인 `id`를 확인하며, 전체 HTML 문법 검사나 브라우저의 오류 복구 동작을 재현하지 않는다.
- 외부 URL·절대경로·다른 문서 내부 연결·Markdown 제목 연결·이미지/미디어 경로·동적으로 생성된 링크는 제외한다. `base href`가 있는 HTML의 상대·목차 연결도 기본 경로를 추정하지 않고 제외 사유를 표시한다. `script`·`style`·`pre`·`code`·`textarea`·`title` 안의 문자열은 링크나 ID로 해석하지 않는다.
- JSON의 `findings`는 발견한 문제, `skipped_checks`는 검사 제외와 그 이유다. `relative_links_checked`·`html_anchors_checked`·`html_ids_checked`는 실제 검사 수다. 다른 파일의 `#대상`은 파일 존재만 검사하고 내부 연결은 별도 제외로 남기므로, 제외 항목 수와 전체 링크 생략 수가 같지 않을 수 있다. `CHECKED_ITEMS_OK`는 검사한 범위에서 문제가 없다는 뜻이다.
- 입력은 `.md`·`.markdown`·`.html`·`.htm`을 지원한다. 다른 형식은 `unsupported_file_type`으로 보고한다. HTML 오류는 `broken_relative_link`·`missing_html_id`·`duplicate_html_id`로 구분하며 원본 파일·줄·대상과 중복 ID의 최초 줄을 필요한 경우 표시한다.
- 링크 오류는 AI가 원문과 대조해 확인한다. 버전 차이·미완료 문구는 사람 또는 AI의 의미 검토 대상이며 도구가 자동 오류로 판정하지 않는다.

### 5.2 HTML 지원과 가벼운 운영

**목적:** 가이드 수정 후 링크·목차를 따로 점검하는 반복 작업을 줄이는 작은 보조 도구로 기존 점검 도구를 확장한다. 지정된 Markdown·HTML 파일을 실행 한 번으로 확인할 수 있게 하되, 설명·명령의 적절성이나 화면 가독성 검토는 필요한 범위에서 별도로 수행한다.

**일상 점검:** AI가 가이드를 작성·수정한 뒤 해당 HTML만 `-Files`로 지정해 로컬에서 1회 구조 점검한다. 검사에서 발견한 오류를 요청 범위 안에서 수정했다면 영향받는 파일만 다시 검사한다. 기존 기본 대상인 Markdown 4개는 유지하고, 매번 HTML 전체를 자동으로 추가하거나 다른 프로젝트까지 스캔하지 않는다. 파일 이동·이름 변경·공통 연결 변경처럼 영향이 큰 경우에 관련 파일 전체로 범위를 넓힌다.

이 절차는 `simple-user-guide`의 공유 원본과 개인 설치본에 연결해 사용한다. 도구·PowerShell 7·자료 접근이 없거나 실행 정책으로 차단되면 원인과 미점검 범위를 보고하고, 자동 설치·정책 변경·우회는 하지 않는다. 예약 실행·원본 자동 수정·Git 작업은 포함하지 않는다. 가이드에 들어 있는 장비·설치·유료 API 명령을 실제로 실행하는 절차와도 구분한다. 내용 정확성·화면 가독성 검토는 별도로 유지한다.

완료 보고의 실제 검사 근거는 [공통 스킬](../../../skills/simple-user-guide/SKILL.md)의 「구조 점검 완료 보고」를 따른다. 보고 형식과 세부 절차를 프로젝트별 AGENTS에 중복 작성하지 않는다.

- 작업기록이나 스킬 연결만으로 절차 준수를 보장하지 않는다. 도구의 동작 확인, 프로젝트 규칙 연결, 실제 가이드 제작 중 AI의 자발적인 점검 수행은 서로 다른 확인 상태로 구분한다.
- 다른 프로젝트의 적용 여부는 다음 실제 가이드 작성 요청에서 추가 검사 지시 없이 규칙 확인 → 작성 → 점검 → 보고가 이어지는지 확인한다. 기존 가이드 재검사만으로 제작 절차까지 검증됐다고 보고하지 않는다.
- 같은 작업에서 변경·오류 없이 통과한 검사를 반복하지 않는다. 오류 수정 후 필요한 재검사는 중복 검사와 구분하며 그 이유를 완료 보고에 남긴다. 별도 기록 시스템이나 보고서 파일은 자동 생성하지 않는다.

지정해 사용할 가이드 예시는 아래와 같다. 이 두 파일은 기본 검사 목록에 자동 추가하지 않는다.

- [Git PC 작업 및 사용 종료 가이드](../../guide_docs/Git_PC_작업_및_사용종료_가이드.html)
- [공통 스킬 사용 및 설치 가이드](../../guide_docs/공통_가이드_스킬_사용_및_설치_가이드.html)

| 구분 | 지원 동작 |
| --- | --- |
| 기존 기능 | 지정 파일의 UTF-8 읽기와 상대 Markdown 링크의 파일·폴더 존재 확인 유지 |
| HTML 파일 연결 | 실제 HTML 링크의 상대 파일·폴더 경로 존재 확인 |
| 같은 HTML 안의 연결 | 목차 등 `#대상` 링크가 같은 문서의 ID에 연결되는지 확인 |
| 다른 문서 연결 | 상대 링크의 대상 파일·폴더 존재만 확인. 다른 문서 내부의 ID 추적은 이번 경량 구현에서 보류 |
| 중복 ID | 점검 대상으로 지정된 각 HTML 문서 안에서 같은 ID가 중복되는지 확인 |
| 오탐 방지 | 주석·코드 예시 속 문자열을 실제 링크로 취급하지 않으며, 한글·공백·URL 인코딩·HTML 문자 참조를 실제 경로·ID와 대조할 수 있게 처리 |
| 결과 표시 | 문제 종류·원본 파일·위치·연결 대상 또는 중복 ID 표시. 검사하지 못한 항목은 이유를 구분하고 정상 검사로 집계하지 않음 |
| 유지할 실행 조건 | PowerShell 7, 지정 파일 중심 조회, 읽기 전용 실행, 기존 종료 코드 0·1·2 유지 |

기존 환경으로 구현 가능한 단순한 방법을 우선한다. 추가 라이브러리는 그 방법으로 요구사항을 충족하기 어려운 근거가 있을 때 검토하며, 새 설치·환경 변경은 별도 허용 범위를 따른다.

외부 웹사이트 접속, 절대경로 확인, 다른 문서 내부의 ID·Markdown 제목 연결, 화면 디자인, 내용 정확성·최신성, 구현 완료·원격 동기화 판정은 이번 확장 범위에 포함하지 않는다. Markdown 참조형·복잡한 문법 지원을 함께 확대하지 않는다. 다른 파일의 `#대상`으로 연결하는 경우 파일 존재만 검사하고 문서 내부 연결은 검사 제외로 구분한다.

점검 도구는 HTML을 실행하거나 브라우저를 조작하지 않는다. 원본·보고서 저장, 자동 링크 수정, Git·네트워크·유료 API 실행을 추가하지 않는다. 검사 완료는 지원하는 링크·ID 검사 결과를 의미하며 화면 검토 완료를 뜻하지 않는다.

### 5.3 검증 결과와 유지 기준

- 최초 구현 검증: [반복 검증 스크립트](../../tools/test_check_project_docs.ps1)의 12개 사례 통과. 정상·오류 HTML, 인코딩·문자 참조, 코드·주석 제외, 다른 문서 연결 제외, 대소문자 구분, Markdown·혼합 입력, 파일·읽기·실행 조건 오류와 원본 무변경을 확인했다.
- 실제 자료 확인: 관리·학습내용정리·네트워크 프로젝트의 가이드 총 8개에서 상대 링크 22곳, 같은 HTML 목차 연결 56곳, ID 56개를 검사했고 지원 범위의 문제를 발견하지 않았다. 검사 전후 원본 내용이 동일했다. 다른 프로젝트 파일은 수정하지 않았다.
- 위 결과는 구조 검사이며 화면·명령의 기술적 정확성·다른 문서 내부 연결·외부 사이트 상태를 검증한 것은 아니다. 별도 검토 에이전트는 이번 구현에 사용하지 않았다.
- 사용자 실행 확인: 최초 일반 터미널 실행은 실행 정책 차단, 다음 시도는 상대 스크립트 경로를 찾지 못해 실패했다. PowerShell 7 실행기·스크립트·프로젝트에 절대경로를 지정한 명령으로 사용자가 통과를 보고했다. AI도 다른 작업 폴더에서 같은 방식으로 `CHECKED_ITEMS_OK`·종료 코드 0을 확인했다. 시스템 실행 정책은 변경하지 않았다.

도구를 변경했거나 새 오류를 재현할 필요가 있을 때 다음을 실행한다. 이 스크립트는 임시 자료만 생성·삭제하며 원본을 수정하지 않는다.

```powershell
& .\tools\test_check_project_docs.ps1
```

- 최초 구현 시 정상 문서와 오류를 넣은 임시 자료로 정상 링크, 깨진 파일 링크, 같은 HTML 안의 없는 ID, 중복 ID를 확인한다. 이후에는 도구 변경이나 새 오류 등 재검증이 필요한 근거가 있을 때 관련 검사를 수행한다.
- 한글·공백·인코딩 경로 및 주석·코드 예시·검사 제외 항목에서 오탐이나 잘못된 정상 판정이 없는지 확인한다.
- 기존 Markdown 검사와 누락 파일·읽기 오류·실행 조건 오류의 동작 및 종료 코드를 유지하는지 확인한다.
- 점검 전후 원본 내용을 대조하고, 검사 실행이 원본을 바꾸거나 보고서·외부 호출을 생성하지 않는지 확인한다. 오류를 넣는 테스트는 원본 대신 임시 자료를 사용한다.
- 수정한 가이드를 지정해 실행 한 번으로 검사할 수 있는지 확인한다. 발견한 문서 문제와 점검 도구의 결함을 구분하며, 요청되지 않은 원본 문서를 자동 수정하지 않는다. Markdown·HTML 혼합 입력과 기존 기본 대상도 최초 구현 때 확인한다.
- 3절에 따라 필요한 검토·수정·재검증을 거쳐 필수 문제를 해결한다. 완료 보고에 변경 내용·실제 검증 근거·검사 제외·남은 사항·실행 방법을 포함한다. 일반적인 가이드 수정에 별도 에이전트 검토나 전체 회귀 검사를 자동으로 요구하지 않는다.
- 이후 도구의 지원 범위가 바뀌면 이 문서의 기능 설명과 README의 점검 도구 설명을 실제 동작에 맞춰 갱신한다. 문서 수정만으로 새 기능의 구현·검증 완료를 기록하지 않는다.

## 6. 스킬 원본과 PC 설치

세 공통 스킬 원본은 상위 [skills](../../../skills/)에 모아 관리한다. 사용 조건은 [상위 AGENTS](../../../AGENTS.md), 생성·수정·검증·보고는 [공통 작업 흐름](../../../docs/common_workflow.md)의 3절을 따른다. 개인 설치본·채팅 등록과 공유 원본 갱신은 별개이며 설치·자동 배포는 별도 요청 범위에서 수행한다.

### 6.1 생성·수정 요청마다 수행할 절차

기존 절 번호는 참조를 위해 유지하며 상세 기준은 공통 작업 흐름 3절로 통합했다. 관리 전용 스킬만 이 프로젝트의 `skills/`를 기본 위치로 하고, 공통 스킬은 상위 `skills/`에 둔다.

## 7. 예약 점검과 효과 확인

- 사용자 결정: 수동 점검을 먼저 검증하고, 예약 시점은 나중에 정한다. 현재 예약을 생성하지 않는다.
- 추후 예약 범위는 지정된 프로젝트의 읽기 전용 점검으로 시작한다. 변경이 없거나 조치할 일이 없으면 조용히 있고, 의미 있는 변경·실패·사용자 결정 필요 시에만 알린다.
- 예약 전 대상·시각·실행 PC와 로컬 접근 조건을 정한다. 자동 파일 반영·Git 동기화·유료 호출은 이 점검에 포함하지 않는다.
- 다음 몇 차례 실제 작업에서 반복 질문·재작업·채팅 재개 준비가 줄었는지 평가한다. 새로운 상시 측정 파일은 만들지 않고, 필요하면 요청된 작업기록에 사례를 남긴다. 사용량 증가도 함께 고려하며 생산성 향상 수치를 미리 보장하지 않는다.
