# 프로젝트 관리 자동화 워크플로

> 버전: 0.3 | 최종 수정: 2026-10-28 | 상태: 승인된 운영 설계와 로컬 구현의 기준

## 1. 목표와 적용 범위

사용자가 마스터 AI와 요구사항·결과를 검토하면 AI가 기획부터 제작·독립 검증·문서화까지 수행하고 완료 근거를 제시한다. 개발, 사용자 가이드, 프로세스 개선, 업무 자동화에 공통으로 적용한다. 역할은 [역할 기준](../00_rules/roles.md), 권한은 [AGENTS](../../AGENTS.md), 공통 기획·점검 도구는 [관리 워크플로](management_workflow.md)가 원본이다.

첫 버전은 herdr 안의 GPT를 유일한 사용자 대화 창구로 두고, ChatGPT Plus·Claude Pro 구독 범위에서 문서·사용자 가이드 프로젝트를 완주하는 것이다. 추가 API 비용·클라우드·Slack 연결은 첫 버전에 포함하지 않는다. 한도 소진 시 상태를 저장하고 대기하며 유료 API로 자동 전환하지 않는다.

이 문서의 운영 목표와 실제 동작 검증을 구분한다. 로컬 상태·증거 검사 도구가 존재해도 herdr→GPT→Claude→Hermes의 자동 전달·결과 회수까지 검증된 것은 아니다. 현재 상태와 실제 증거는 [작업기록](../04_records/management_log.md) 및 해당 실행 기록을 따른다.

## 2. 요구사항과 단계

**공통 흐름:** 요구사항·대표 결과 확인 → 기획 ↔ 검토 → 제작·실행 ↔ 검토 → 독립 QA → 문서화 ↔ 검토 → 완료 판정.

| 단계 | 입력 | 결과와 다음 단계 조건 |
| --- | --- | --- |
| 요구사항 | 왜, 무엇을 누구를 위해, 어떻게 만들 것인지에 대한 요청 | 대표 결과와 사용자 합의 명세. MVP·제외 범위·완료 기준·제약을 명시 |
| 기획 | 승인 명세 | 요구사항 번호에 연결된 실행계획. Claude 검토의 필수 결함 해결 |
| 제작·실행 | 승인 계획과 고정된 입력 | 기능·문서·처리 결과 및 자체 시험. GPT 검토의 필수 결함 해결 |
| 독립 QA | 승인 명세, 고정된 산출물, 시험 입력·환경 | 정상 사용·예상 오류 처리·발견 결함에 대한 실제 시험 증거 |
| 문서화 | 변경 결과와 QA 증거 | 관련 wiki·가이드 갱신, 원본과 설명의 일치 검토 |
| 완료 | 각 단계 결과와 증거 | 필수 결함 없음, 합의 시험 통과, 가이드 검증, 남은 제한·미검증 공개 |

- 사용자 합의용 요구사항·작업명세와 AI 실행용 실행계획을 구분한다. 작은 프로젝트는 한 문서의 두 부분으로 합칠 수 있다. 명세를 실행계획에서 다시 정의하지 않는다.
- 사용자는 목적·결과·범위를 승인하고 AI가 상세 기술·실행 방법을 제안한다. ‘어떻게’에 사용자가 기술 해답까지 작성할 필요는 없다.
- Phase는 검토 가능한 큰 결과, Task는 기능·산출물 단위, Step은 Task 내부 실행 순서다. 작은 작업은 Phase 하나로 줄이며 날짜·완료율을 임의 확정하지 않는다.
- 사용자가 볼 수 있는 대표 결과를 먼저 검토한다. 앱은 화면 목업, 가이드는 대표 한 페이지, 자동화는 입력·출력 예시다. 복잡한 인터뷰는 실제 규모·불확실성이 요구할 때만 한다.
- 불필요한 의존성과 결합을 줄이되 검증된 도구 재사용을 허용한다. 의존성을 높이는 것 자체를 리팩토링 목표로 삼지 않는다.
- 개발자의 자체 시험은 필수이며 자신의 결과 최종 승인과 구분한다. 검토는 범위를 확대하지 않지만 변경으로 인한 기존 기능 손상·데이터 손실을 지적할 수 있다.

### 2.1 Task 설계와 세션 전환

요구사항·기획 단계부터 각 Task의 산출물, 담당 역할과 새 세션, 입력·출력, 완료·검토·인계 조건을 설계한다. 기존 실행계획에 Task ID와 명세 버전을 연결하며 별도의 같은 명세 사본을 만들지 않는다. 짧은 작업도 작업 단위와 책임은 식별하되 불필요한 Phase·문서를 늘리지 않는다.

- 작업 단위마다 새 담당 세션을 기본으로 한다. 같은 Task의 결함 수정·재검증은 기존 세션을 재사용할 수 있으며 제작과 독립 검토·QA는 분리한다. 독립적인 조사만 병렬로 진행하고, 수정은 담당 파일과 순서를 정해 동일 파일 쓰기 충돌을 금지한다.
- 새 세션에는 부모 대화 전체 대신 목표, 확정 결정, 필요한 원본의 절·줄, 금지·보류 사항, Task ID·명세 버전, 입출력·완료·검토·인계 조건을 전달한다. 자료를 읽었다는 기록만으로 이해·적용 완료를 판정하지 않는다. 담당자는 작업 범위와 완료 조건을 확인하고 결과·증거로 적용을 보여준다.
- 예상보다 작업이나 맥락이 커지면 마스터에 알리고, 기존 공식 작업기록·실행 기록에 완료 근거와 남은 작업·다음 입력을 인계한 뒤 새 세션에서 이어간다. 마스터가 결과를 종합해 사용자에게 보고한다. 승인 범위 안의 세션 분할만으로 재승인을 요구하지 않으며 비용·핵심 범위 등 주요 변경은 기존 승인 기준을 유지한다.
- 새 세션 생성·전달·결과 회수는 실제 연결 기능으로 확인한다. 자동화되지 않은 전달은 수동 인계로 표시하고 세션 생성 완료나 전체 자동화를 주장하지 않는다. 도구가 지원하지 않는 연결은 미구현·미검증 상태와 다음 행동을 남긴다.

### 2.2 맥락 복원

1. 공식 작업기록의 최신 절·인계에서 현재 작업과 다음 행동을 찾는다. 문서 제목·색인과 필요한 범위부터 읽으며 전체 로그를 기본 입력으로 삼지 않는다.
2. 관련 결정·요구사항·설계 원본을 대조하여 유효한 범위·버전·보류 조건을 확인한다. 누락·충돌이 있을 때 필요한 과거 절까지 점진적으로 넓힌다.
3. 현재 대화의 미저장 결정과 진행 내용을 대조하여 이번 작업 맥락에 반영한다. 공식 파일 저장은 허용된 반영 범위를 따르며, 미저장 내용은 그 상태를 표시한다.
4. 결정 완료, 미구현, 미검증, 미정·보류를 구분해 다음 Task의 입력과 완료 조건을 정한다. 결정 완료를 기능 구현·시험 완료로 바꾸어 요약하지 않는다.

## 3. 상태·증거·재시도

상태는 대기·진행·검토·수정·차단·완료로 구분한다. 승인 명세, 산출물, 검토·시험 증거가 없거나 필수 결함이 남으면 완료로 넘어가지 않는다. 상태 도구는 기록된 구조와 파일 일관성을 검사하며 내용의 진실성을 대신 판정하지 않는다.

- 시험마다 요구사항 번호, 시험 조건, 대상 버전, 예상 결과, 실제 결과, 증거 위치, 수행 세션을 기록한다. 화면이 없는 작업은 로그·출력 파일·대조 결과를 증거로 사용한다.
- 정상 사용은 대표 성공 결과를 남기고, 예상 오류 처리는 예상된 메시지·데이터 보존을 확인한다. 실제 발견 결함은 재현과 수정 후 확인을 연결한다. 캡처 개수 제한 때문에 필요한 근거를 삭제하지 않는다.
- 소스만 보고 QA 시나리오를 만들지 않는다. 승인 요구사항에서 기본 시나리오를 만들고 소스는 위험 요소를 보완할 때 확인한다.
- 같은 필수 결함이 두 차례 수정 후에도 반복되거나 재평가 없이 세 차례 검토를 초과하면 마스터 재평가로 전환한다. 재평가는 원인·시도 결과·수정 방향을 기록한다. 도구는 재평가 후 현재 회차 카운터를 새로 시작하되 전체 검토 이력과 이벤트는 보존하며, 누적 횟수와 현재 회차를 혼동하지 않는다.
- 로그인 실패, 도구 부재, 한도 소진, 실행 실패, 검증 불일치를 차단 사유로 구분한다. 실패한 호출이나 단순 종료를 작업 성공으로 해석하지 않는다.
- 실행·작업 ID로 중복 요청을 식별한다. 중단 후 마지막 완료 단계와 남은 Task를 확인하고, 진행 중 작업은 실제 산출물·세션 상태를 확인한 뒤 재개한다. 완료 작업을 무조건 다시 실행하지 않는다.
- Phase 보고에는 결과·검증 방법·근거·남은 제한을 담는다. 진행 알림과 검증된 완료 보고를 구분한다. ‘확정·제안·미정·보류·미검증’ 및 예외·실패·승인 조건은 요약에서 보존한다.

## 4. 기록과 문서 책임

```text
프로젝트/
├─ docs/
│  ├─ 기존 규칙·요구사항·설계·기록
│  └─ workflows/<실행ID>/
│     ├─ 00-request/
│     ├─ 01-planning/
│     ├─ 02-development/
│     ├─ 03-qa/
│     ├─ 04-wiki/
│     ├─ raw/
│     ├─ state.json
│     └─ timeline.md
├─ wiki/
│  ├─ index.md
│  └─ adr/
└─ guide_docs/
```

실행 폴더는 실행할 때 생성한다. `02-development`는 경로 호환을 유지하고 비개발 작업에서는 제작·실행 기록으로 사용한다. `04-wiki`는 갱신 대상과 검토 증거를 보관하며 wiki 전체 사본을 만들지 않는다.

| 위치 | 고유 책임 |
| --- | --- |
| 요구사항·실행계획 | 이번 작업에서 합의한 범위와 실행 방법 |
| `state.json` | 도구가 읽는 현재 실행 상태·근거 참조 |
| `timeline.md` | 시간순 사건·판정 및 원문·증거 링크 |
| `raw/` | 수집 가능한 메시지·도구 실행·출력 원문. 자동 수집 여부·누락 범위 명시 |
| `wiki/` | 현재 유효한 구조·운영 설명과 결정 기록 |
| `wiki/adr/` | 중요한 결정의 배경·선택·이유·영향 |
| `guide_docs/` | 사용자가 따라 할 최종 가이드 |

내부 추론이나 접근 불가능한 메시지를 ‘전체 원문 수집’에 포함했다고 주장하지 않는다. 인증정보는 원문 수집 단계에서 제외하고 누락 사실을 남긴다. Obsidian은 같은 Markdown을 읽는 창구로 사용하며 별도 사본을 기본 생성하지 않는다. 상세 상태를 관리 요약과 wiki에 중복 유지하지 않는다.

### 4.1 process_debug On/Off

`process_debug`는 작업 진행 근거를 사용자 응답에 요약해서 보여주는 선택 기능이다. On/Off는 추가 점검 수집과 요약 표시를 제어하며 Off에서도 기본 `raw/`·`timeline.md`·`state.json`의 증거와 상태 기록은 유지한다. Off 기간의 사용량·문서 조회를 나중에 측정한 것처럼 소급 집계하지 않는다. 이미 없는 원문이나 수집하지 못한 증거를 Off 상태라는 이유로 숨기거나 존재한다고 표시하지 않는다.

On에서는 응답별로 실제 담당 세션의 Task 별칭과 ID, 연결된 명세 Task·버전, 참조한 문서의 절·줄, 사용 규모 요약을 표시한다. 확인되지 않은 세션 ID나 사용량은 미확인으로 남긴다. 사용 규모는 실제로 확보한 입력·출력 길이 등 대리 지표에 따른 추정일 수 있으며 측정 출처·범위·추정 여부를 함께 표시한다. 문서 참조 기록은 읽기·전달의 근거이고 이해의 증명이 아니다.

컨텍스트는 현재 요청에 제공된 맥락 규모, 누적 토큰은 측정 가능한 호출의 사용량 합계, 구독 한도는 제공자가 표시하는 계정 제한으로 구분한다. 서로 환산하거나 추정치를 실제 토큰·남은 구독량으로 보고하지 않는다. 시스템이 공개하지 않는 컨텍스트 잔량·내부 추론·다른 세션 원문은 자동 수집할 수 있다고 가정하지 않는다.

운영 절차는 [process-debug 스킬](../../skills/process-debug/SKILL.md), 로컬 보조 기능은 [process_debug.py](../../tools/process_debug.py)를 따른다. 도구에 전달한 자료와 실제 자동 수집 자료를 구분하고, 실행마다 수집 출처·누락·지원하지 않는 범위를 남긴다. 파일 기반 요약 도구 구현과 전체 세션 자동 관찰·전달의 구현은 별개다. 응답 표시 형식은 이후 프로토타입 검증에서 조정하되 기본 증거·불확실성 구분을 유지한다.

## 5. 환경·도구·비용

- 운영 영역의 herdr·마스터·기록과 Docker 작업 영역의 개발·빌드·시험을 분리한다. 허용 폴더·네트워크·비밀정보 접근을 제한하며 Docker만으로 완전한 격리가 입증되었다고 하지 않는다. Docker 실행 전 호스트에서 수행한 검사는 그 사실을 명시한다.
- Hermes는 MCP 서버를 통해 도구를 사용하는 에이전트다. 모델·인증·과금 경로를 따로 확인한다. 추가 비용 없는 연결이 성립하지 않으면 스크립트로 운영 기록을 처리하는 제한형 프로토타입까지만 진행하고 Hermes 통합은 미완료로 남긴다.
- herdr는 사용자 창구·세션 관리 기반이며 프로젝트 승인·재시도·완료 판단은 이 워크플로가 담당한다. 설치, 로그인, 작은 작업 전달·회수, 전체 프로토타입 완주를 각각 검증한다.
- pstack은 필요한 검증·리뷰 절차부터 호환성을 확인한다. 원본의 Cursor 의존 기능이나 프로젝트 규칙과 충돌하는 실행 방식은 자동 도입하지 않는다. 전체 이식은 첫 버전 필수 조건이 아니다.
- fork는 캐시 적중·비용 절감 보장이 아니다. 공통 규칙을 안정적으로 유지하고 관련 원본·변경분만 전달한다. 독립 QA에 제작자의 긴 대화를 전달하여 캐시를 높이는 방식은 사용하지 않는다.
- 신규 도구는 기존 도구로 해결할 수 없는 경우 출처·권한·비용·제거 방법을 확인하고 승인 범위에서 설치·최소 시험한다. 설치 성공과 실제 연결 성공은 구분한다.
- VPC 이전을 위해 실행 설정·영속 기록·인증정보·경로·메신저 연결을 분리한다. 다른 환경에서 재기동·기록 복원을 검증하기 전에는 이전 가능 완료로 표시하지 않는다.

공식 근거 확인일: 2026-10-27. [herdr 설치](https://herdr.dev/docs/install/), [Hermes 모델 연결](https://hermes-agent.nousresearch.com/docs/integrations/providers), [pstack 원본](https://github.com/cursor/plugins/tree/main/pstack), [OpenAI 캐시](https://developers.openai.com/api/docs/guides/prompt-caching), [구독·API 비용](https://learn.chatgpt.com/docs/pricing). 제공자의 기능·요금제는 변경될 수 있으므로 실제 연결 시 다시 확인한다.

## 6. 구현·검증 순서

1. herdr에서 GPT·Claude 실행, 구독 인증, 모델 선택, 작은 요청 전달·결과 회수를 확인한다. Hermes 무추가비용 연결은 별도 확인한다.
2. ‘AI에게 작업 요청하기 → 진행 상태 보기 → 중단 후 재개하기’ 가이드로 대표 페이지·명세 승인부터 제작·독립 QA·문서화까지 수행한다.
3. 깨진 링크, 필수 안내 누락, 실행 결과 불일치, 반복 결함, 세션 중단, 도구 부재·로그인 실패·한도 제한을 시험한다. 미해결 사항과 근거가 요약에서 보존되고 검토자가 원본을 수정하지 않는지도 확인한다.
4. 실제 결과·증거·미검증·다음 행동을 보고한다. 로컬 엔진 시험 통과만으로 서로 다른 LLM의 교차 검증이나 단일 대화 창구 완주를 선언하지 않는다.

Task 새 세션 인계·맥락 복원과 process_debug On/Off의 실제 적용은 별도 실행 근거로 확인한다. 이 환경 정비만으로 보류된 가이드 제작이나 Claude 전송을 재개하지 않는다. 보류 해제 후 프로토타입에서 표시 형식·인계 누락·새 세션의 작업 이어받기를 검증한다.

## 7. 로컬 상태 도구

[workflow.py](../../tools/workflow.py)는 Python 표준 라이브러리 기반의 오프라인 상태·증거 관리 도구다. Python이 있는 터미널에서 이 프로젝트 폴더를 기준으로 실행한다.

```powershell
python -X utf8 tools/workflow.py --help
python -X utf8 tools/workflow.py doctor
```

`doctor`는 도구 경로를 찾는다. 인증·과금·Docker 실행 성공을 확인하지는 않는다. `status`와 `report`는 `--id`에 실제 실행 ID를 지정하여 저장된 단계 상태·다음 단계·무결성 문제·한계를 읽는다. `timeline`은 저장된 이벤트에서 시간순 색인을 다시 만든다.

`init`은 승인 명세를, `start`·`submit`·`review`·`complete`·`block`·`resume`·`reassess`·`reopen`은 단계별 인계·판정 입력을 받는다. 입력 JSON은 `--packet`의 프로젝트 상대경로로 지정하며, 상태 변경에는 `--stage`와 중복 방지용 `--op`를 사용한다. 같은 작업을 재시도할 때 같은 operation ID를 재사용한다. 서로 다른 입력에 같은 ID를 사용하지 않는다. [입력 항목 안내](../../tools/workflow_packets.md)와 도구 구현을 함께 따른다.

실패 QA도 기록하고 실패 상태에서는 통과를 막는다. `reopen`은 마스터 근거를 받아 해당 단계와 후속 승인을 무효화한다. 이전 제출·검토·증거 파일은 회차 기록과 내용 해시 스냅샷으로 보존한다. 재작업은 검토 횟수를 초기화하지 않으며 반복 결함 차단은 먼저 `reassess`로 해소한다. 네 번째 검토가 통과여도 누적 반복을 마스터가 재평가해야 한다. 증거는 파일당 20MB 이하이며 알려진 인증 문자열이 있으면 복사 전 거절한다. 이미지에 보이는 민감정보나 임의 형식 비밀까지 자동 검출하지는 않는다.

도구는 파일 존재·내용 해시와 입력 항목·상태 전이를 검사한다. 제출자가 사실과 다른 검토자·세션·통과 결과를 입력했는지 자체 인증하지 않으므로 원문과 실제 수행 증거의 대조가 필요하다. 원문은 도구에 명시적으로 제출한 JSON이며 전체 채팅을 자동 수집하지 않는다. 알려진 인증정보 패턴 검사는 모든 민감정보 탐지를 보장하지 않으므로 입력 준비 시 비밀정보를 제외한다.

검사 결과 코드 0은 명령 처리 성공, 1은 조회된 증거 무결성 문제, 2는 입력·상태·파일 처리 오류를 뜻한다. 코드 0만으로 전체 실행 완료가 되는 것은 아니며 결과의 완료 여부와 미검증 한계를 확인한다. 동시 변경 잠금이 남았다면 실제 작업 프로세스 종료 여부를 먼저 확인하고, 상태 파일을 직접 수정하여 검사를 우회하지 않는다.
