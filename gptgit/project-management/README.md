# 프로젝트 관리 개선

> 문서 버전: 0.27 | 최종 수정: 2026-11-06 | 상태: 프로젝트 관리·개선

GPT 공통 운영 방법은 [상위 README.md](../README.md), AI 행동 규칙은 [상위 AGENTS.md](../AGENTS.md)를 따른다. AI의 commit·push는 각각 사용자의 명시적인 실행 요청이 있을 때만 수행한다.

## 목적과 범위

이 프로젝트는 여러 프로젝트에 적용할 공통 실행 환경·작업 절차·기본 틀을 구성하고 개선한다. 개별 신규 프로젝트는 별도 폴더에 개설하며 소스·문서·진행 기록은 그 프로젝트에서 관리한다. PM 역할로 작업 범위·우선순위·진행 상태·프로젝트 간 의존성을 관리하고, 디렉터 역할로 목표·설계 방향·작업 기준·결과물의 품질을 검토한다. 조언자 역할로 사용자가 정한 방향을 달성할 더 나은 방법을 능동적으로 제안한다.

자동화 운영은 이 관리 프로젝트의 현행 기능이 아니다. 이전 목표와 절차는 [자동화 워크플로](wiki/architecture/automation_workflow.md)에 과거 설계·운영 자료로 남아 있으며, 당시 구현·연결·검증 이력은 [작업기록](docs/04_records/management_log.md)과 관련 근거에서 확인한다. 이 기록의 자동화 실행 계획은 이번 사용자 지시에 따른 현행 기능을 뜻하지 않는다.

관리 대상은 사용자가 지정한 프로젝트다. 개별 프로젝트의 실행 환경·소스·설정·상세 작업기록은 해당 프로젝트에서 관리한다. 이곳에서는 원본의 위치를 연결하고, 프로젝트 간 조정과 공통 개선에 필요한 내용을 관리한다.

## 역할 구분

| 역할 | 핵심 질문 | 담당 업무 |
| --- | --- | --- |
| PM | 무엇을 언제, 어떤 순서로 진행할까? | 범위·우선순위·진행 상태·의존성·장애 요인 관리, 다음 작업과 인계 정리 |
| 디렉터 | 무엇을 목표로, 어떤 수준까지 만들까? | 목표·설계 방향·문서 구조·작업 기준 결정 지원, 결과물의 목적 적합성과 품질 검토 |
| 조언자 | 같은 목표를 더 효과적으로 달성할 방법이 있을까? | 대안·장단점·비용·작업 부담 비교, 추천과 선택 지원 |
| 실행 담당 | 어떻게 구현하고 적용할까? | 승인된 범위의 구현·설정·문서 작성·수정과 자체 시험 |
| 검토·독립 QA 담당 | 완료 근거가 충분한가? | 읽기 전용 검토와 별도 세션의 실제 사용 시험 |

관리 역할과 과거 자동화 설계의 담당을 구분한다. 마스터 GPT·기획 GPT·제작 Claude·검토·독립 QA·Hermes 운영의 과거 책임과 인계는 [역할 기준 기록](wiki/architecture/roles.md)에 남아 있다. 역할 정의만으로 별도 에이전트 생성이나 실제 연결이 완료되는 것은 아니다. 사용자는 프로젝트 목표와 주요 방침 변경의 최종 결정자다.

## 사용자와 AI의 협업

사용자는 목표·우선순위·주요 방향을 결정하고, 직접 접근해야 하는 환경의 설정 적용·실행·결과 제공을 담당한다. AI는 관리·설계 검토·대안 제시와 접근 가능한 범위의 작성·수정·검증을 담당한다. 실제 분담은 프로젝트 규칙과 작업별 요청에 따라 정하며, 사용자에게 필요한 작업은 목적·순서·완료 확인 방법을 함께 안내한다.

더 좋은 방법이 보이면 별도 질문을 기다리지 않고 코멘트한다. 사용자의 목표와 학습 목적을 기준으로 현재 방법과 대안의 효과·작업량·비용·전환 영향을 비교하고 추천 이유를 설명한다. 목표 자체의 재검토가 필요하면 그 이유를 밝힌다. 주요 방향 변경은 사용자와 결정하고, 사용자가 기존 방향을 선택하면 그 조건 안에서 개선한다.

## 작업 시작

1. 이 문서와 [AGENTS.md](AGENTS.md)를 확인한다.
2. 작업 대상 프로젝트의 최신 README와 AGENTS에서 기준 문서와 소스 위치를 확인한다.
3. 요청에 필요한 현재 상태·설계·기록·증빙만 확인한다.
4. 진행 관리·방향·품질 검토를 수행하고, 유의미한 대안이 있으면 조언한다. 결과와 사용자·AI의 다음 작업을 정리한다.

이미 확인한 자료는 변경·누락·충돌이 있을 때 추가 확인한다. 대화 기억만으로 최신 상태를 확정하지 않는다.

「작업기록 읽고 다음 작업 이어나가자」라는 요청으로 재개할 수 있다. 최신 인계·관련 원본과 이번 작업에 필요한 PC 환경 차이를 확인한 뒤 허용된 작업을 이어간다. 상세 절차와 인계 형식은 [공통 작업 흐름](../docs/common_workflow.md)을 따른다.

## 확인된 프로젝트의 진입점

전체 프로젝트·자료 폴더의 실제 진입점은 [상위 README](../README.md)에서 관리한다. 이곳에 Library 식별 경로나 프로젝트 목록 사본을 중복 유지하지 않는다. 상세 상태는 각 프로젝트의 공식 원본에서 확인한다.

## 문서 진입점과 폴더 구조

위키는 원본의 내용을 주제별로 분해·합성해 설명하는 공간이다. 분류와 출처·상태 보존 기준은 [위키 편집 기준](wiki/AGENTS.md), 형식의 단일 기준은 [위키 스키마](skills/wiki-editor/references/schema.md)에서 확인한다. 원문별 주제와 설명 페이지의 대응은 [내용 분류표](wiki/index/content_classification.md)에서 찾는다. 문서 편집과 실제 기능 구현·동작 검증은 구분한다.

현재 설명과 상세 문서는 [wiki 색인](wiki/index.md)과 아래 여섯 폴더에서 찾는다. [raw](raw/)는 원래 구조를 보존한 과거 보관 원본이다. 세 공통 스킬은 상위 `../skills/`, 관리 전용 도구는 `tools/`에서 관리한다. wiki 문서 이동 중에는 상세 경로를 색인이나 해당 폴더에서 확인한다.

```text
프로젝트 관리 개선/
    README.md
    AGENTS.md
    docs/04_records/management_log.md  # 최신 인계와 남은 업무
    wiki/
        index.md                       # 탐색 창구
        features/                      # 기능
        architecture/                  # 구조와 설계
        decisions/                     # 결정
        index/                         # 색인
        log/                           # 기록
        operations/                    # 운영
    raw/                               # 원래 구조의 과거 보관 원본
    guide_docs/                        # 사용자 가이드의 지정 저장 위치
```

위 목록은 주요 진입점이다. 개별 프로젝트마다 같은 문서를 강제로 만들거나 기존 내용을 즉시 분리하지 않는다. 이곳에 개별 프로젝트의 소스·상세 작업기록 복사본을 두지 않는다. 사용자 가이드는 `guide_docs/`에 둔다. 실행 기록·wiki·가이드의 책임은 [wiki 색인](wiki/index.md)에서 확인한다.

작업기록: [management_log.md](docs/04_records/management_log.md) — 최신 인계와 기록 당시 남은 8개 업무를 확인한다. 기록상 이 업무의 실행 대상은 project-prototype이며, 발견한 문제의 분석과 개선 결정은 이 관리 프로젝트에서 다룬다. project-prototype은 개선된 프로세스를 독립적으로 적용하는 시험 프로젝트다. 자동화 운영의 현행 기능 여부는 이번 사용자 지시가 우선한다.

## 기획·인계·점검 도구

Claude 전용 운영 문서·스킬은 [별도 운영 폴더](../../automation-agents/claude/README.md)에 새로 작성해 관리한다. 작업 위치와 소스·기록은 이 프로젝트에 유지한다. [Claude 시작기 보관본](raw/tools/start_claude.ps1)은 과거 외부 지침·설정 연결에 사용한 자료이며 현재 실행 가능 여부는 확인되지 않았다. 기존 Claudecode 문서를 재사용하지 않는다.

[프로젝트 관리 열기](프로젝트 관리 열기.lnk)는 이 PC용 바로가기 파일이다. 당시 구현은 ‘새 프로젝트 만들기 / 기존 프로젝트 열기 / 관리 환경 점검’을 구분하고, 모델 호출 없이 최소 기본 틀 1.0으로 개설하거나 기존 문서를 변경하지 않고 세션을 여는 범위였다. 초기 진입점 기록의 AI 연결 전 상태와 후속 세션 시작기·수신기의 구현·모의 시험은 시점을 구분해야 한다. 이 바로가기와 보관 도구의 현재 실행·호환, 실제 대화 복원은 이번 문서 편집에서 확인하지 않았다. 제공 범위는 [진입점 기능](wiki/features/project_entry.md), 후속 설계와 검증 한계는 [세션 구조](wiki/architecture/agent_session_lifecycle.md)에서 확인한다. 다른 PC의 경로·바로가기는 그 환경에서 별도로 확인한다.

공통 재개·스킬 생성 검증·인계는 [공통 작업 흐름](../docs/common_workflow.md)에서 관리한다. 관리 워크플로는 관리 역할의 실행·검토 분담과 문서 점검 도구 운영을 맡는다.

아래 기획·인계 스킬과 상위 `skills/`의 가이드 스킬은 gptgit 하위 프로젝트에서 공통으로 사용한다. 사용 조건과 원본 위치는 [상위 공통 규칙](../AGENTS.md)을 따르며, 각 프로젝트의 상세 규칙·기록·실행 권한을 유지한다.

- [신규 프로젝트 요구사항 작성 양식](wiki/features/신규_개발_프로젝트_요구사항_작성양식.md): 사용자가 목적·가치·범위를 정의하고 AI에게 상세 기획을 맡기는 입력 문서.
- [관리 워크플로](wiki/operations/management_workflow.md): 초기 기획, 실행·검토 분담과 인계의 현행 기준 진입점. 과거 점검 도구의 명령·예약 조건은 [과거 문서 점검](wiki/operations/historical_document_checks.md)에서 구분한다.
- [자동화 워크플로 기록](wiki/architecture/automation_workflow.md): 과거 승인 명세·실행계획과 단계·증거·비용·환경 설계.
- [자동화 역할 기준 기록](wiki/architecture/roles.md): 과거 마스터·제작·검토·독립 QA·운영의 책임과 세션 구분.
- [로컬 워크플로 도구 보관본](raw/tools/workflow.py): 과거 실행별 상태·인계 입력·증거 파일을 관리한 도구다. 실제 LLM 호출이나 세션 전달은 수행하지 않으며, 검토자 신원은 입력된 선언이므로 별도 실행 근거가 필요하다. 현재 실행 가능 여부는 확인되지 않았다.
- [project-planning 스킬 원본](../skills/project-planning/SKILL.md): 아이디어·요구사항에서 첫 버전의 구체적인 기획안을 구성한다.
- [project-handoff 스킬 원본](../skills/project-handoff/SKILL.md): 최신 인계와 근거를 대조해 현재 상태·다음 행동을 정리한다.
- [위임·보고 스킬](skills/delegation-reporting/SKILL.md): 이 프로젝트의 승인된 Codex CLI 위임과 지속 승인된 업무별 날짜 보고 작성·누적 기준.
- [수동 문서 점검 도구 보관본](raw/tools/check_project_docs.ps1)과 [도구 테스트 보관본](raw/tools/test_check_project_docs.ps1)은 과거 상대 링크·HTML 구조 점검에 사용한 자료다. 현재 도구로서의 실행 가능 여부는 확인되지 않았다. 점검은 최신성·구현 완료·화면 품질을 판정하지 않는다.

스킬 공유 원본은 Git 관리 대상이며 개인 설치본은 PC별로 별도 관리한다. pull만으로 개인 설치본이 갱신되지는 않는다. 정기 예약은 수동 점검을 먼저 검증한 뒤 추후 정한다. 개별 프로젝트의 실행 규칙과 보류 상태는 이 도구 도입으로 바뀌지 않는다.

## 과거 자동화 설계·운영 자료

다음 자료는 과거 설계·운영과 그 근거를 확인하기 위한 기록이다. 이 관리 프로젝트의 현행 자동화 기능이나 실행 안내가 아니다.

- [process-debug 스킬 보관 원본](raw/skills/process-debug/SKILL.md): 과거 `process_debug On/Off` 절차 기록. 현행 적용 의무는 없다.
- [점검 도구 보관본](raw/tools/process_debug.py): 과거 사용량 관측·집계 도구. 현재 실행 가능 여부는 확인되지 않았다.
- [Hermes 작업 연결 설계](wiki/architecture/hermes_worker.md): 과거 제한형 전달·회수 설계와 제한.

당시 실행 상태는 [작업기록](docs/04_records/management_log.md)을 확인한다. 환경 시험은 전체 제작→독립 QA→문서화 프로토타입의 완료를 뜻하지 않는다. 가이드 정식 제작·기존 자료 전송 보류는 유지한다.

## 사용자 가이드

## 문서 책임과 중복 방지

| 자료 | 담당 내용 | 변경 시점 |
| --- | --- | --- |
| README.md | 목적·범위·역할 요약·문서 위치·진입점 | 목표·관리 대상·경로가 바뀔 때 |
| AGENTS.md | AI가 따라야 하는 행동·조회·검증·수정 규칙 | 작업 방식·권한·보고 기준이 바뀔 때 |

| raw | 원래 구조를 보존한 과거 보관 원본 | 과거 근거 확인이 필요할 때 |

위치·목적은 README, 현행 행동·권한은 AGENTS에 둔다. 자동화 워크플로와 자동화 역할 기준은 과거 설계·운영 자료다. 동일 규칙을 여러 곳에서 중복 관리하지 않는다. 현재 방침과 과거 변경 이력은 구분한다.

## 파일 조회와 반영 원칙

현재는 초기 단계이므로 논의 내용을 자동으로 파일에 반영하지 않는다. 필요한 파일 조회는 요청된 검토·조언을 위해 수행하되, 파일·폴더 생성, 내용 수정·저장, 이동·이름 변경·삭제 등 실제 반영은 사용자가 명시적으로 요청한 범위에서만 수행한다. 자세한 실행 기준은 AGENTS의 「파일 조회와 반영 요청」을 따른다. 이 원칙은 사용자가 변경할 때까지 유지한다.

## 방침 변경과 문서 수정

README와 AGENTS는 수정 가능한 Markdown 원본이며 영구 고정 규칙이 아니다. 사용자의 변경 지시에 따라 현재 기준을 갱신한다.

1. 변경할 방침과 이유, 영향을 받는 프로젝트·문서를 확인한다.
2. 목적·범위·위치는 README, AI 행동 규칙은 AGENTS의 해당 절을 수정한다. 상세 방침 문서가 생겼다면 그 기준 절을 먼저 갱신한다.
3. 영향을 받는 연결·설명도 함께 수정하고, 현재 규칙 간 모순을 확인한다.
4. 의미 있는 방침 변경 시 버전을 올리고 수정일을 갱신한다. 변경 이력은 해당 문서에 남기고 중요한 선택의 이유는 `wiki/decisions/`에서 관리한다. 같은 결정을 다른 위치에 중복 관리하지 않는다.
5. 개별 프로젝트의 방침 변경이 필요하면 적용 대상을 명시한다. 이곳의 수정만으로 다른 프로젝트의 문서가 수정되거나 규칙이 자동 적용된 것으로 보지 않는다.

로컬 AI 도구에서 사용할 때는 실제 작업 폴더에도 AGENTS와 참조 문서를 배치해야 한다. 단순한 파일 보관이나 역할 정의만으로 에이전트가 자동 생성되지는 않는다.
