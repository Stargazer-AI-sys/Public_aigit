### %1 최초 조회

- 공식 작업기록은 머리말과 최상위 제목(`##`)을 먼저 조회해 최신 인계를 찾는다. 머리말의 절 번호와 실제 마지막 인계 제목이 다르면 관련 부분만 확인해 기준을 정한다. 고정 줄 번호나 README의 절 번호만으로 최신 여부를 판단하지 않는다.
- 최신 인계의 하위 제목(`###`) 중 **현재 작업 위치·실행 제약 및 검증 한계·남은 작업**에 해당하는 소절부터 읽는다. 현재 17절에서는 **17.1·17.6·17.7**이다. 이후 인계의 번호·형식이 달라지면 같은 역할의 소절을 선택하고, 분리되어 있지 않으면 필요한 인계 본문까지 조회한다.
- 여기서 다음 작업과 제약을 파악할 수 있으면 최초 조회를 마친다. 최신 인계 전체·1~16절·요구사항 전체·가이드·소스 트리를 기본 조회 대상으로 묶지 않는다. 확인한 구간에 필수 결정·보류 조건의 다른 절 참조가 있으면 해당 구간을 추가 확인한다.

### %3 조회 방법과 과거 기록의 취급

- `rg -n '^## ' docs/04_records/학습내용정리_작업기록.md`로 인계 위치를 찾고, 해당 인계 범위에서 하위 제목을 확인한다. 본문은 확인한 시작 제목부터 다음 같은 수준 또는 상위 제목 직전까지 읽는다. PowerShell에서는 현재 검색 결과의 줄 번호를 이용한 `Get-Content … | Select-Object -Skip … -First …` 등으로 출력 범위를 제한한다.
- 자료·함수 위치가 불명확하면 지정된 소스 폴더나 관련 문서에서 파일명·함수명·주제어를 검색하고 일치 구간만 읽는다. 검색 결과가 많거나 출력이 잘리면 파일·절·검색어 범위를 좁힌다. 동일한 전체 출력을 반복하지 않는다.
- 과거 절의 “현재 상태·다음 작업”은 당시 이력이다. 최신 인계에서 유효한 설계·근거로 참조한 구간이나 현재 문제의 원인 확인에 필요한 구간만 조회한다. 요구사항의 과거 구현 상태 설명도 최신 인계·실제 관련 소스와 구분한다.
- 패키지 `v0.5`, 기본 Schema `v0.2`, 인터페이스 설계 `v0.1`, 과거 Schema `v0.1`·`v0.2` 초안은 서로 다른 버전이다. 작은 버전 번호만으로 폐기하거나, 과거 prototype·ZIP을 현재 소스로 선택하지 않는다. 실제 작업 대상은 최신 인계가 지정한 로컬 수정본이며, 인계 이후 변경은 현재 관련 소스와 대조한다.
- 부족한 근거·충돌·환경 차이가 있을 때만 조회를 넓힌다. 조회량을 줄이기 위해 현재 작업의 보류 조건·실행 제약·검증 한계를 생략하지 않는다.

## $Notion 게시·검증과 반복 실행 기준

### %1 적용 범위와 재사용 원본

- Notion 게시·동기화·검증·새 자료 자동화의 관련 코드를 수정하거나 실행할 때 적용한다. 다른 작업에서 Notion을 조회하거나 전체 테스트를 반복 실행하라는 규칙은 아니다.
- 반복 전달·응답 저장·중단 관리·대조 코드는 [tools/notion_bridge](../../study/study-system/tools/notion_bridge/)의 `run_dispatch.js`·`dispatch.js`·`state.mjs`·`verify.py`를 먼저 확인해 재사용한다. 같은 기능의 큰 임시 실행 코드를 매번 새로 조립하거나 터미널에 전체 응답을 붙여 넣지 않는다. 필요한 경로·대상·실행 옵션만 전달한다.
- 게시 로직은 기존 [notion_mcp.py](../../study/study-system/analyzer/notion_mcp.py)·[notion_sync.py](../../study/study-system/analyzer/notion_sync.py)를 재사용한다. 실행 데이터는 기존 `study/study-system/output/notion_live/`의 `bridge/`·`runs/`·`outbox/`에 유지한다. 코드와 실행 데이터를 혼합하거나 복구 목적으로 영수증·대기 결과·잠금을 임의 삭제하지 않는다.
- 로컬 코드 저장은 독립 인증·무인 게시 구현과 별개다. 실제 호출은 연결된 Notion 도구를 사용하고, 이 규칙을 새 유료 분석·스키마 변경·게시·Git 실행의 포괄 허가로 확대하지 않는다.

### %2 조회 축소와 보존 조건

1. 원격 본문을 읽기 전에 현재 승인 계획과 로컬 영수증을 비교해 변경 후보를 계산한다. 자료 한 건의 변경이라도 공유 개념·주제·관계·읽기 링크의 실제 영향 범위를 포함한다.
2. 기존 항목은 목록 조회의 ID·동기화 키·관리 해시/작업 값과 Notion 자체 수정 시각을 확인한다. 로컬 내용이 같고 원격 수정 시각도 영수증과 같으며 미완료 작업이 없는 경우, 저장된 결과를 재사용해 본문 조회와 쓰기를 생략한다. 원격 관리 해시만으로 수동 수정이 없다고 판단하지 않는다.
3. 수정 시각은 대상 설정의 `revision_property`와 실제 `last_edited_time` 속성에 연결돼 있어야 한다. 관리 속성은 학습 화면에서 숨긴다. 시각이 달라졌거나 없고, 새 항목·로컬 변경·불확실한 중단 상태·충돌 등의 근거가 있으면 필요한 페이지 본문을 조회한다. 증거가 없는데 무변경으로 간주하지 않는다.
4. 삭제·중복·수동 수정 감지를 위한 목록 조회는 유지하고, 추가 페이지가 있으면 끝까지 확인한다. ‘기존 본문 조회 생략’을 ‘Notion 조회 전체 생략’으로 표현하지 않는다. 목록의 추가 페이지·관리하지 않는 항목·기능 미지원 때문에 호출 수가 달라질 수 있다.
5. 과거 영수증에 수정 시각 기준이 없으면 최초 1회 본문·속성을 기존 영수증과 대조해 로컬 기준만 보충할 수 있다. 다음 무변경 실행까지 이 확인을 반복하거나, 기준 추가를 이유로 승인 자료 본문·관계를 다시 쓰지 않는다.
6. 응답 유실·중단 시 저장된 항목별 결과와 실제 상태를 확인한 뒤 미완료 부분만 복구한다. 이미 보낸 요청의 결과가 불확실하면 자동 재전송하지 않는다. 사용자 수동 수정은 덮어쓰지 않고 충돌로 보고한다.

### %3 변경 후 검증과 완료 판정

- 먼저 저장 결과와 관련 로컬 테스트를 활용한다. 실제 Notion 실행은 요청 범위와 검증 필요가 있을 때만 수행하며, 문서 확인·상태 보고만을 위해 다시 게시하지 않는다. 검증되지 않은 실행을 완료로 기록하지 않는다.
- 관련 검증은 [test_notion_delta.py](../../study/study-system/tests/test_notion_delta.py), 기존 `test_notion_mcp.py`·`test_notion_sync.py`, 전달/대조 코드의 `test_notion_bridge.cjs`·`test_notion_bridge.py`를 선택한다. 영향을 받는 테스트를 실행하고 동일 근거로 이미 통과한 검사를 불필요하게 반복하지 않는다.
- **무변경:** 기준이 있는 관리 항목의 불필요한 본문 조회 0·쓰기 0·중복 생성 0을 확인한다. 목록 조회는 유지한다. 현재 4개 관리 DB가 각각 한 페이지 이내일 때 목록 조회 4회가 기준 예시이며, 모든 규모에 고정된 호출 수로 강제하지 않는다.
- **일부 변경·신규 자료:** 변경된 자료와 영향받는 공유 항목만 본문을 읽고 갱신하는지, 무관한 기존 항목의 ID·내용·승인을 보존하는지 확인한다. 로컬 분석 재사용·재승인 방지와 Notion 조회 축소의 검증을 구분한다.
- **오류·복구:** 관리 해시는 그대로인데 본문만 수정한 경우, 삭제·중복, 수정 시각 미확인, 목록 페이지 나눔, 본문 반영 후 속성 저장 중단의 해당 영향 사례를 확인한다. 전달 코드 변경에는 긴 한글·인용부호·Windows 경로·분할 응답과 중단 후 재전송 방지를 포함한다.
- 보고에는 대상·변경 범위, 목록 조회/본문 조회/쓰기/재사용/초기 기준 확인 건수, 오류·미완료, 승인 DB 불변을 구분한다. `request_json_bytes`·`response_json_bytes`는 논리적 JSON 크기이며 네트워크 실전송량·모델 토큰·요금이 아니다. 신규·전체 개편·기준 추가·정상 무변경·복구 실행을 혼합해 절감률을 계산하지 않는다.
- `verify.py`는 저장된 응답의 로컬 대조다. 이를 원격 최신 상태 확인이나 실제 화면 검증으로 보고하지 않는다. 현재 기준의 실행 근거는 [조회 축소 검증 결과](../../study/study-system/output/notion_live/delta/report.json)에서 확인할 수 있다. 결과 파일이 없거나 코드·대상이 바뀌면 관련 소스·테스트로 확인하고, 과거 수치를 현재 실측값처럼 재사용하지 않는다.

## $가이드 문서 작성 규칙 (2026-10-15)

### %1 공통 절차의 기준

- 명시적으로 요청된 가이드 작성·수정에는 `simple-user-guide`를 사용한다. 공통 작성 방식·HTML 틀·로컬 1회 구조 점검은 [공유 원본 SKILL.md](../../../skills/simple-user-guide/SKILL.md)에서 관리한다. 실행 명령과 검사 절차를 이 문서에 중복 작성하지 않는다.
- 형식·디자인의 기존 참고 HTML은 과거 자료로 유지한다. 새 작성·수정의 공통 기준은 스킬의 틀이며, 사용자가 별도 형식을 지정하면 해당 지시를 따른다. 형식 확인을 위해 여러 과거 가이드를 반복 조회하지 않는다.

### %2 이 프로젝트의 내용 조건

- Collector·Analyzer·JSON·Schema 등의 용어는 처음 사용할 때 역할을 쉬운 말로 설명한다. 기존 프로젝트의 `$` 상위·`%` 하위 카테고리 표기를 유지한다.
- 관련 최신 소스·Schema·작업기록·실행 증거에서 사용 방법과 내용을 확인한다. 초기 테스트 구현이나 과거 예시를 최신 인터페이스로 취급하지 않는다.
- 수집 입력, Collector 추출 결과, Analyzer 입력, 최종 AI 분석 결과와 실행 상태 기록을 구분한다. 실제 Schema의 필드명·필수/선택 항목·검증 기준을 사용하고, 임시 식별값·축약 본문을 운영 데이터로 안내하지 않는다.
- JSON·분석 예시는 실제 Schema와 대조하고 가능한 범위에서 검증한다. 구조 검사 통과와 원문 근거·분석 내용의 사실성 검토를 구분한다.
- 기능·설계 가이드는 목적·사용 흐름·실제 예시·확인 기준과 사용자에게 필요한 범위를 중심으로 작성한다. 현재 실행 가능한 기능·설계·미구현 기능을 구분하며, 문서 작성이나 로컬 구조 점검을 API·실제 동작 검증 완료로 기록하지 않는다.
- 검증 결과에는 실제 환경·대상·확인 범위·미검증 범위를 구분한다. 작업기록 갱신 요청에 가이드 상태를 포함할 때도 갱신 여부와 적용 범위를 구분한다.

### %3 저장·반영 조건

- 기본 위치는 `guide_docs/`이며 사용자 지정 위치가 있으면 그 지시를 따른다. 기존 가이드는 같은 파일을 갱신하고, 문서의 식별자·수정일·버전 이력을 유지한다. 별도 사본은 사용자 요청이나 실제 보관 필요가 있을 때만 만든다.
- 가이드·작업기록의 갱신 시점과 범위는 아래 「가이드 및 작업기록 반영 시점·범위」를 따른다. 공통 스킬 연결은 자동 문서 생성·상시 갱신 허가가 아니다.

## $가이드 및 작업기록 반영 시점·범위 (2026-10-12)

### %1 사용자가 요청한 시점에만 반영

- 사용자 가이드 문서와 공식 작업기록은 매 작업·구현·검증 때마다 자동으로 작성하거나 갱신하지 않는다.
- 사용자는 최종적으로 진행해야 할 작업이 단계별로 완료되면 반영 시점을 정해 요청한다. 단계 완료 자체를 문서 반영 요청으로 간주하지 않는다.
- `가이드에 반영해줘`, `작업기록에 반영해줘` 등 명시적인 요청이 있을 때 요청한 문서만 작성·갱신한다. 둘 다 요청한 경우에만 두 종류의 문서에 반영한다.
- 작업 중에는 구현·검증을 진행하고 결과를 대화에서 안내한다. 문서 반영 요청이 없다는 이유로 작업을 중단하거나 매번 반영 여부를 묻지 않는다.

### %2 요청 시 context 확인과 필요한 내용 선별

- 반영 요청을 받으면 해당 시점까지의 대화 context, 사용자 결정·수정 지시, 실제 소스·결과물·검증 상태 및 대상 문서의 현재 내용을 확인한다.
- 사용자 가이드에는 사용자가 준비·실행·결과 확인·문제 해결에 필요로 하는 변경 부분만 쉬운 한국어로 반영한다. 개발 과정의 모든 대화·시도·임시 내용을 그대로 옮기지 않는다.
- 작업기록에는 단계별 최종 완료 사항, 확정된 설계·결정, 실제 검증 결과·한계, 미완료 항목과 다음 작업 중 필요한 내용만 반영한다. 중간 시도·폐기된 방향을 최종 상태처럼 기록하지 않는다.
- 기존 내용과 겹치는 부분은 통합하고 필요한 항목은 누락 없이 반영한다. 가이드와 작업기록의 역할을 구분하며, 변경 범위의 참조·수정은 상위 공통 조회 원칙을 따른다.
- 실제 실행·검증한 범위와 설계·구현 예정 범위를 구분한다. 대화나 임시 파일만으로 완료 상태를 추정하지 않는다.

### %3 기존 규칙과의 적용 관계

- 위 반영 시점·범위 규칙은 기존 문서 및 작업기록에 있는 자동 갱신·수시 반영 취지의 문구보다 우선한다.
- 기존 가이드의 형식·저장 위치·동일 문서 갱신·검증 규칙은 사용자가 문서 반영을 요청한 경우에 적용한다.
- 규칙 문서 수정 요청은 해당 규칙 문서만 수정하는 요청이다. 별도 요청 없이 사용자 가이드나 작업기록까지 함께 갱신하지 않는다.
