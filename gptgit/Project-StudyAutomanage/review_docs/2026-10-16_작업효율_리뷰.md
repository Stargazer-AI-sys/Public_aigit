## 1. 리뷰 결론

최초 리뷰의 **해결된 보류의 재발·무관한 자료의 재승인·분석 조건 비교 전 재사용**은 후속 구현으로 개선했다. 이후 묶음 생성·왕복 축소·호출 계측도 구현했지만 **전체 본문 반복 조회와 전달·복구 비용은 여전히 크다.** 사용자 화면은 DB 연결을 완료 기준으로 삼은 탓에 의도와 어긋났으며, 후속 개편으로 수정했다. 다음 개선은 게시 읽기량을 줄이고, 게시와 사용자 화면 갱신을 연결하는 것이다.

2~6절은 해당 시점의 근거·계획이다. 최신 리뷰와 사용자가 정한 진행 순서는 **7절**을 따른다. 구현·검증 상태는 공식 작업기록 최신 인계를 확인한다. 이번 리뷰 문서 반영 자체를 위해 프로그램 테스트나 실제 전송을 재실행하지 않았다. 공통 관리 자료와 Project-management는 개선 대상에서 제외한다.

## 3. 유지할 방식

- 저장 응답·모의 응답으로 우선 검증하고 코드 검증을 위해 유료 API를 반복 호출하지 않는다.
- 문서만 수정할 때 전체 프로그램 테스트를 다시 실행하지 않는다. 변경 영향에 맞는 검사만 수행한다.
- 정상 통과한 검사는 새 변경·실패·미해결 문제가 있을 때만 반복한다.
- 사용자 본문·분류 편집을 현재 단계에서 제외하고 승인·보류에 집중한다.
- 자동 유료 재시도 0회, 누적 한도 100회/$2를 유지한다. 실제 잔여값은 필요할 때 `budget`으로 확인한다.

## 4. 다음 작업 순서와 완료 기준

1. **상태·재사용 판단 개선:** 같은 사유의 보류 재발 방지, 무관한 정책 변경 시 승인 유지, 실제 분류/본문 변경 시 승인 무효화, 분석 조건 변경 시 잘못된 재사용 차단을 검증한다. 임시·복사 저장소를 사용하며 실제 승인 DB를 시험용으로 변경하지 않는다.
2. **프로젝트 전용 조회·상태 확인:** 최신 인계·관련 절·승인/보류 수·다음 작업을 짧게 출력한다. 조회 불가 상태를 0건으로 표시하지 않으며 인증정보·전체 원문을 기본 출력하지 않는다.
3. **Notion 연동:** 전송 예정 내용 확인 → 로컬 모의 전송 → 대상·권한·반영 범위 확인 후 대표 1건 실제 전송 → 재실행 중복 방지 → 실패 복구 순서로 검증한다. Notion 수동 수정과 재전송의 충돌 처리도 확정한다.
4. **신규 자료 자동화:** 변경된 자료만 처리하고 새 승인·오류·충돌을 사용자가 확인하게 한다. 사용자 승인을 자동 승인으로 바꾸지 않는다.

현재 다음 작업은 작업기록 20절의 인계를 따른다. 이 절의 순서는 최초 계획이며 1~3의 대표 검증은 이후 진행됐다. 리뷰 제안 자체를 유료 호출·외부 전송·Git 실행 허가로 취급하지 않는다.

## 6. Notion 작업 시간과 과도한 반복에 대한 후속 리뷰

사용자는 자료가 정상적으로 올라간 것은 확인했지만, 작업이 오래 걸렸고 단순 게시라면 내용을 하나하나 전부 검증해야 했는지 의문을 제기했다. 이 지적을 개선 과제로 수용한다. 승인된 분석을 게시할 때 필요한 저장 검증과 학습 내용의 사실성 검토를 구분해야 한다. 이미 승인된 동일 내용의 게시 때문에 원문과 기술 내용을 다시 전수 검토할 필요는 없다.

### 7.1 확인 범위와 실제 사용량

근거는 [화면 개편 실행 보고서](../study/study-system/output/notion_live/runs/20261019T011714Z_c06511548b2e/report.json)와 `analyzer/notion_mcp.py`의 `inventory`·`write_many`다. 72페이지를 목록 구성·쓰기 전 충돌 확인·본문 반영 확인·최종 확인에서 반복 조회했다. 별도의 복구 조회·안내 화면 구성·브라우저 검사 등은 위 계측에 포함되지 않는다. 전체 개편·중단 복구 실행이므로 신규 자료 한 건의 정상 비용이나 기존 실행과의 동일 조건 성능 비교로 사용하지 않는다.

저장된 `output/notion_live/reader/remote_pages.json`은 72개 응답·337,257바이트였다. 응답의 `text` 합계는 266,478자이며 상위 DB 구조 설명의 반복은 73,060자로 약 27%다. 문자량·파일 크기는 모델 토큰 수·과금액·실제 네트워크 전송량과 다르며, 정확한 토큰 비용이나 절감률은 현재 자료로 확정할 수 없다.

### 7.2 사용량이 남아 있는 원인과 개선 기준

- 앞선 개선은 생성 묶음 처리와 파일 교환 왕복 축소에 집중했다. 한 묶음 안의 페이지 조회 수와 큰 응답량까지 줄인 것은 아니다.
- 변경 없음으로 쓰기를 건너뛰더라도 `inventory`에서 전체 페이지 본문을 먼저 가져온다. 로컬 영수증과 승인본을 비교해 변경 후보를 좁히는 과정이 원격 조회보다 먼저 필요하다. 공유 개념 등 실제 영향받는 대상은 함께 계산해야 한다.
- 정상 경로의 전체 본문 확인이 중복된다. 사용 가능한 도구의 작은 응답으로 원격 수정·존재를 판별할 수 있는지 먼저 확인하고, 지원되지 않으면 필요한 대상의 본문 조회를 유지한다. 정상 처리와 응답 유실·충돌·복구의 검증 수준을 구분한다.
- 원격 관리 해시만으로 수동 수정 여부를 판단하면 안 된다. 사용자가 본문을 바꿔도 관리 해시가 그대로일 수 있다. 실제 원격 변경 감지와 승인 보존을 유지한 상태에서 조회를 줄인다. 로컬 무변경 판단과 원격 동기화 검증도 구분한다.
- 큰 응답은 프로그램에서 저장·대조하고 모델에는 차이·건수·오류 요약만 전달한다. 이는 대화 입력량을 줄이는 조치이며 Notion 자체 응답 크기까지 줄였다는 뜻은 아니다. 전달·인코딩·중단 복구의 반복 비용도 별도로 줄인다.
- 개선 효과는 동일한 입력·변경 범위로 측정한다. 무변경·일부 변경·신규 자료·수동 수정 충돌·응답 유실을 나눠 읽기/쓰기 횟수, 요청/응답 바이트, 전체 본문 조회 대상, 복구 횟수·시간을 기록한다. 쓰기 0만으로 사용량 개선 완료를 판단하지 않는다.

### 7.3 사용자 화면 의도가 어긋난 원인

사용자의 의도는 관리용 DB에 저장한 데이터를 시안에 맞춘 학습 화면에서 탐색하는 것이었다. 최초 구현은 DB 연결 보기를 배치하고 페이지 간 이동이 가능하면 화면 구성이 끝났다고 판단했다. 관리용 데이터 구조와 사용자 화면의 완료 기준을 구분하지 못한 구현·검증 판단의 문제다.

- 시안을 화면별 행동·표시 내용·관리 정보 노출 기준으로 구체화하지 않았다.
- 데이터·관계 저장은 확인했지만 실제 개념 페이지에 관리 속성과 긴 관계 목록이 먼저 보이고 주제 본문은 비어 있는 문제를 사전에 잡지 못했다.
- 실제 브라우저에서 시안과 비교하기 전에 학습 홈 구성 완료라고 보고했다. 이후 DB 4개·연결 보기 19개를 관리/보관 영역으로 옮기고 DB 항목 72개의 본문·안내 화면 10개를 개편하는 재작업이 발생했다.
- 현재 화면 구성은 수정했지만 홈·찾아보기는 생성된 읽기용 본문이다. 항목 게시 이후 안내 화면 자동 갱신 연결은 아직 남아 있다. 외형 수정과 지속 운영 완료를 구분해야 한다.

앞으로 대표 사용자 흐름 하나를 실제 Notion에서 먼저 완성해 시안과 비교한 뒤 나머지로 확장한다. 데이터 보존·게시 성공·화면 사용성은 별도 완료 기준으로 검증하고 보고한다. 새 자료가 게시됐을 때 필요한 사용자 화면도 함께 갱신되는지를 운영 완료 기준에 포함한다.

### 7.4 사용자가 정한 진행 순서

1. **게시 사용량 개선:** 위 변경 후보 선별·조회 축소·전달 안정화·바이트 계측을 우선한다. 충돌 감지·중복 방지·승인 보존·복구 동작을 유지하면서 동일 조건의 조회량 감소를 검증한다.
2. **사용자 화면 갱신 연결:** 게시 성공 후 기존 안내 페이지 ID를 재사용해 영향받는 홈·분야·찾아보기만 갱신한다. 변경 없는 화면의 불필요 쓰기와 중복 생성은 0을 목표로 검증한다.
3. **신규 자료 자동화 확장:** 위 게시 경로를 재사용해 파일 변경 탐지·분석 필요 판단·승인 대기로 연결한다. 입력 위치·실행 주기는 구현 시 필요한 범위만 확인하며 자동 승인은 하지 않는다. 새 유료 분석은 별도 허용 후 수행한다.

이 순서는 사용자가 이번 대화에서 확정했다. 순서 확정과 리뷰 저장을 각 개선의 구현 완료로 표현하지 않는다. 무거운 게시 경로를 그대로 예약 실행하는 방식으로 자동화를 먼저 확대하지 않는다.

### 7.5 활용할 도구·스킬

- 기존 Notion 연결: 실제 DB/페이지 접근에 사용한다. 작은 원격 상태 응답 지원 범위를 확인하고 현재 연결을 재사용한다. 별도 서비스 도입이나 인증 방식 변경부터 시작하지 않는다.
- 기존 Python·SQLite·회귀 테스트: 영수증·변경 범위 비교·응답 대조와 사용량 계측의 중심으로 사용한다. 반복 JSON 처리와 비교를 모델의 수동 작업으로 남기지 않는다.
- 브라우저 제어: 시안과 실제 대표 화면·이동 흐름을 확인한다. 전체 데이터 검증을 브라우저 반복 클릭으로 대체하지 않는다.
- 공유 `project-handoff`: 최신 인계·근거를 좁게 확인할 때 사용한다. `project-planning`은 사용자 화면 요구를 구체화할 필요가 있을 때 사용하고, `simple-user-guide`는 명시적으로 요청된 가이드 갱신에 사용한다.
- `notion-database-designer`는 기존 DB의 구조·관계 변경이 실제로 필요한 경우에 적용한다. 사용자 화면 검증을 이 스킬의 DB 구성 완료만으로 대신하지 않는다.

현재 작업을 시작하는 데 추가 플러그인·스킬 설치는 필수가 아니다. 위 스킬 이름의 언급은 이후 적합한 작업에서의 활용 제안이며 설치·새 스킬 제작·각 스킬의 실제 실행 완료를 뜻하지 않는다.
