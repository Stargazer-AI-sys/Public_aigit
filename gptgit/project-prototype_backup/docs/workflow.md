# 자동화 프로세스

> 버전 0.1 | 2026-11-04 | 정책·운영 설계. 전체 실행 검증 완료를 뜻하지 않음

권한 원본은 [AGENTS](../AGENTS.md), 실행 전 입력 기준은 [프로세스 적용 조건](requirements.md), 담당 입력은 [컨텍스트 기준](context-and-agents.md)에 둔다.

## 1. 단계와 승인

| 단계 | 담당·입력 | 결과·통과 조건 |
| --- | --- | --- |
| 요구사항 | 사용자＋마스터: 목적·제약·대표 결과 | 요구사항 ID, 범위·비목표·완료 조건·실행 권한을 담은 작업명세서 확정 |
| 기획 작성 | Codex 담당: 작업명세서의 관련 범위 | 개발기획서: 요구사항 추적, 설계·인터페이스·Task·시험·담당·쓰기 범위 |
| 기획 통합 | 마스터 또는 지정 통합 담당 | 병렬 결과의 중복·상충·의존성 제거, 하나의 고정 검토 버전 |
| 기획 검토 | Claude: 작업명세서＋개발기획서 | 누락·충돌·실행 가능성·QA 가능성에 대한 근거 있는 결함/통과 의견 |
| 기획 승인 | 마스터: 검토와 수정 근거 | 필수 결함 해소 및 작업명세 일치 확인, 개발 Task 배분 |
| 개발 | Claude 제작 담당: 승인된 Task와 관련 소스 | 코드·자체 시험·변경 설명·제한, 고정 산출물 버전 |
| 독립 QA | 제작자와 다른 담당 세션: 요구사항·시험 계획·결과물 | 실제 입력/예상/실제·환경·근거·결함; 제작자의 성공 보고로 대체 금지 |
| 개발 통과 | 마스터: QA 및 수정·재시험 근거 | 필수 결함 해소, 요구사항별 증거 충족 |
| 문서화 | Hermes: 전달된 결과·근거·제한 | 작업기록·wiki 초안. 근거 밖 사실·완료 상태 추가 금지 |
| 문서 검토·완료 | 마스터 또는 별도 검토 담당 | 초안과 실행 근거 대조 후 승인 범위 저장·최종 보고 |

독립 QA 담당의 제공자·모델은 작업 계획에 명시한다. 기본적으로 Codex 별도 세션을 사용할 수 있으나 제작 검토와 독립 실행 QA를 같은 것으로 표시하지 않는다. 같은 계열의 별도 세션 검토와 서로 다른 제공자의 교차 검증도 구분한다.

## 2. 기획 작성↔검토 루프

1. Codex 기획 담당이 작업명세서의 요구사항 ID를 개발기획서의 설계·Task·검증 조건에 연결한다.
2. 통합 담당이 병렬 결과의 인터페이스와 의존성을 조정하고 검토 버전을 고정한다.
3. Claude는 그 버전과 작업명세를 읽어 필수 결함·선택 개선·범위 밖 제안을 구분한다. 직접 원본을 수정하지 않는다.
4. 마스터가 의견과 근거를 판정해 해당 Codex 담당에게 필요한 수정만 반환한다.
5. 수정 버전과 변경 근거를 재검토한다. 필수 결함이 없고 요구사항·시험·역할 인계가 충족되면 마스터가 개발을 승인한다.

새로운 기능 제안을 기획 검토 중 조용히 필수 요구로 바꾸지 않는다. 요구사항 변경이 필요하면 영향과 추천안을 사용자에게 제시한다.

## 3. 개발↔독립 QA 루프

1. 승인된 개발 Task를 Claude에 전달한다. 제작자는 수정 대상과 자체 시험 결과를 반환한다.
2. QA는 승인된 요구사항과 고정 결과물을 기준으로 실제 시험한다. 소스 구현을 그대로 따라 만든 시험만으로 수락 기준을 대체하지 않는다.
3. 마스터가 재현 가능한 필수 결함을 제작자에게 반환한다. 제작자는 수정 후 영향받는 시험을 수행하고 QA가 해당 결함 및 필요한 회귀 범위를 다시 검증한다.
4. 마스터가 요구사항·버전·실행 근거를 대조해 통과 판정한다. 제작자의 자체 시험과 QA 결과를 각각 보존한다.

기획 검토 루프와 이 루프를 모두 적용한다. 실제 자동 전달·재검토·독립 QA 실행 여부는 각각의 실행 증거로 확인한다.

## 4. 연속 진행·재평가·중단

사용자가 실행을 승인한 명세 안에서는 마스터가 선행 단계 통과 후 다음 Task를 진행한다. 필수 입력·권한·비용·보류·실행 실패가 있으면 해당 작업만 차단하고 독립된 허용 작업은 계속한다.

- 같은 필수 결함이 두 차례 수정 후에도 반복되거나 재평가 없이 세 차례 검토를 초과하면 마스터 재평가로 전환한다. 네 번째 검토 결과가 통과라도 재평가를 생략하지 않는다.
- 재평가는 원인·시도·변경 방향·다음 조건을 기록한다. 현재 회차와 전체 누적 이력을 구분한다. 세션·Task ID를 바꿔 이력을 지우지 않는다.
- timeout·연결 실패·불명확 응답은 실제 세션·요청 도달·결과를 확인한다. 성공이 불명확한 동일 요청을 자동 반복하지 않는다. Hermes는 AGENTS의 엄격한 재전송 기준을 적용한다.
- 인증·구독 확인 실패, 한도 소진, 도구 부재, 미해결 권한, 검증 불일치를 실패 종류별로 보고한다. API나 다른 유료 모델로 자동 전환하지 않는다.
- 완료 작업은 이유 없이 반복하지 않는다. 수정된 경로·버전·인터페이스에 필요한 검증만 추가한다.

## 5. 기록과 원본

작업명세서는 사용자 합의, 개발기획서는 실행 설계, 실행 기록은 상태·근거, wiki는 현재 설명을 맡는다. 같은 상세 상태를 여러 곳에서 관리하지 않는다.

승인된 실행의 Task 완료·차단·재평가에는 해당 실행 기록을 갱신한다. Phase 종료·마스터 교대에는 [공식 작업기록](records/work_log.md)에 요약과 근거 위치를 남긴다. 초안 작성·마스터 검토·파일 저장·실제 화면 확인을 각각 구분한다. 일반 논의는 자동 저장하지 않는다.

기록에는 작업/Task ID, 명세·산출물 버전, 담당·실제 세션 ID, 입력과 결과 위치, 시험 조건·실제 결과, 제한·보류·다음 행동을 남긴다. 인증값과 접근 불가능한 내부 추론은 수집하지 않는다. 상태 도구의 형식 검사 통과만으로 사실·독립성·완료를 판정하지 않는다.
