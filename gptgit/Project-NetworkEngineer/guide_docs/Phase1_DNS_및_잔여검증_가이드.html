Phase 1 DNS·잔여 검증 가이드

기존 인터넷 IP 통신 검증 이후 진행한 DNS 설정, 관리망 주소 확인, 누락된 장비 정보와 통신 증거 확인을 정리합니다.

이 문서는 이번 채팅에서 제공된 출력과 사용자 성공 보고를 바탕으로 작성했습니다. 장비 명령은 사용자가 실행합니다. 이미 완료한 항목은 재실행하지 않으며, 환경 변경·장애·근거 누락이 있을 때 관련 단계만 사용합니다. 최신 상태의 공식 기준은 진행상황, 이력은 작업기록입니다. 이번 가이드 작성은 두 MD의 결과 갱신을 포함하지 않습니다.

EDGE 인터넷·NAT 가이드까지 수행한 환경을 전제로 합니다. 새로 구성하는 경우에는 해당 선행 가이드부터 확인합니다.

2. PC20 DNS 설정·저장·재시작

PC20 VPCS 콘솔. 이번 시작 상태는 외부 IP Ping 성공, Cannot resolve example.com, DNS 주소 비어 있음이었습니다. 기존 출력이 없다면 아래 조회로 확인합니다.

show ip
ping 1.1.1.1
ping example.com

숫자 IP Ping은 성공하지만 DNS가 비어 있고 이름 해석이 실패할 때 DNS 서버를 지정합니다. DNS가 이미 지정돼 있다면 덮어쓰지 말고 기존 값과 실패 출력을 확인합니다.

ip dns 1.1.1.1
show ip
ping example.com

확인: DNS 1.1.1.1 표시, 도메인의 IP 해석과 응답 여부를 각각 확인합니다. 이번 출력은 example.com resolved to 104.20.23.154, Ping 5/5 성공입니다. 도메인이 반환하는 IP는 시험 시점에 달라질 수 있으며 이 숫자를 고정 설정하지 않습니다.

성공 후 PC20에서 저장합니다.

save

저장 유지 검증이 아직 없을 때만 PC20 노드를 정상 종료 후 다시 시작합니다. PNETLab 전체나 외부 DNS 서버를 재시작하는 작업이 아닙니다.

show ip
ping example.com

완료 기준: DNS 설정 유지, 이름 해석·통신 성공. 이번에는 저장과 PC20 재시작 후 유지까지 사용자가 확인했습니다. 같은 결과를 다시 요청할 필요가 없습니다.

이번에 바꾼 값은 비어 있던 PC20 DNS뿐입니다. 검증 실패 시 오류 출력을 먼저 확인합니다. 이번 변경만 되돌릴 필요가 있을 때의 VPCS 명령은 ip dns 0이며, 실제 원복 시험은 수행하지 않았습니다.

3. Linux 임시 경로·관리망 DHCP 확인

임시 경로 제거 여부

Linux 테스트 서버 터미널. 기존 삭제 결과가 미수집이었으므로 조회했습니다.

ip route show 1.1.1.1/32

이번 결과: 출력 없음. 조회한 현재 라우팅 테이블에 해당 /32 경로가 없으며 삭제 명령은 필요하지 않습니다. 전체 정책 라우팅 검증을 뜻하지는 않습니다.

주소 출처가 기록과 다를 때만 확인

ip -4 addr show dev ens32
nmcli -f GENERAL.CONNECTION,IP4.ADDRESS,IP4.GATEWAY,DHCP4.OPTION device show ens32

첫 명령은 현재 주소·dynamic·유효기간을, 두 번째는 활성 연결과 DHCP 서버·임대 IP를 확인합니다. 필요한 출력은 GENERAL.CONNECTION, IP4.ADDRESS, IP4.GATEWAY, DHCP4의 ip_address·dhcp_server_identifier·dhcp_lease_time입니다. 관련 없는 옵션 행은 생략해도 됩니다.

수동 등록값과 자동 할당 방식을 구분해야 할 때만 연결 프로필을 조회합니다. 이번에 확인한 ens32 UUID를 사용한 명령입니다.

nmcli -f connection.id,ipv4.method,ipv4.addresses,ipv4.gateway,ipv4.dns connection show uuid 7fa2bb2b-abd5-39d1-a648-0c15abce21ef

프로필이 없다는 오류가 나면 nmcli -f NAME,UUID,DEVICE connection show에서 DEVICE가 ens32인 행만 확인합니다. (END)는 q로 종료합니다. 이번 환경에서 지원하지 않았던 --pager no 옵션은 사용하지 않습니다.

저장 원본과의 충돌까지 확인해야 할 때만 sudo netplan get network.ethernets를 추가 실행하고 ens32 아래 addresses·dhcp4·gateway4 또는 routes·nameservers만 확인합니다. 매번 세 종류의 조회를 모두 수행하지 않습니다.

이번 근거판단
Netplan addresses .100/24, dhcp4 true / 프로필 method auto.100 수동 주소와 DHCP를 함께 사용하는 구성
.128 dynamic, DHCP ip_address .128, 서버 .254, 임대시간 1800초현재 .128은 DHCP 임대 주소
VMware VMnet8 DHCP Settings .128~.254 — 사용자 확인확인된 수동 .100과 EDGE .110은 할당 범위 밖

FIX: 과거 사용자는 .100·.128 모두 직접 입력했다고 설명했습니다. 현재 출력은 .128 DHCP 임대를 보여줍니다. 변경 경위는 미확인이며 과거 입력 사실을 부정하지 않습니다. 두 주소가 있다는 사실이나 .128이 DHCP 범위 안이라는 이유만으로 충돌이라 판단하지 않습니다.

완료 기준: 현재 주소 출처와 확인된 수동 주소·DHCP 범위의 관계 확인. 이번에는 설정을 바꾸지 않았습니다. 다른 VM 전체의 주소·임대 목록은 미점검이므로 관리망 전체의 무충돌을 보장한 결과는 아닙니다. 실습 VLAN용 DHCP 서버 구성과도 별개입니다.

4. 이미지 전체 이름 보완

이전 기록에 IOSvL2 Access/Core 기본 기능과 IOSv 라우팅·NAT 동작은 확인돼 있었습니다. 이번 요청 목적은 잘리거나 누락된 Image 전체 이름 보완입니다. 이미지 재선정·기능 재시험이 아닙니다.

PNETLab 노드의 Edit 화면에서 Image 값을 조회합니다. 실행 중 열리지 않으면 장비를 끄지 말고 해당 확인만 보류합니다. 화면에 Template 항목이 없으면 추가 조작을 요구하지 않습니다.

대상사용자가 확인한 Image 전체 이름
ASW1 / CORE-TESTviosl2-adventerprisek9-m.ssa.high_iron_20200929
EDGE-TESTvios-adventerprisek9-m.spa.159-3.m9

IOSvL2의 기존 show version은 15.2(20200924:215240), EDGE는 IOSv 15.9(3)M9입니다. Image 이름과 실행 버전 문자열은 구분합니다. 과거 IOL L3 후보는 Core 스위치 역할에서 제외됐습니다.

5. 양방향 통신·ARP·MAC·라우팅·NAT 증거

이번에는 미수집이던 포트별 증거와 잔여 자료를 보완했습니다. 장애·구성 변경이 없고 해당 출력이 이미 있다면 반복 수집하지 않습니다.

PC20 → PC10

PC20 VPCS 콘솔.

ping 10.10.10.10

이번 결과: 사용자 성공 보고. 기존 PC10 → PC20 성공 기록과 함께 양방향 통신 근거로 사용합니다. 이번 역방향 시험의 전체 손실률 출력은 별도 수집하지 않았습니다.

CORE-TEST의 # 프롬프트

show ip route
show ip arp

확인: VLAN10·20 및 10.255.0.0/30 직접 연결, 기본 경로 via 10.255.0.2. ARP의 PC10·PC20·EDGE IP와 MAC을 대조합니다. Linux ARP가 없다는 사실만으로 장애를 판단하지 않습니다.

PC20: NAT 정보가 만료되기 전에 조회할 수 있도록 연속 Ping을 시작합니다.

ping 1.1.1.1 -t

-t는 연속 시험입니다. EDGE-TEST # 프롬프트:

show ip route
show ip nat translations

확인: 내부 10.10.10.0/24·10.10.20.0/24 via 10.255.0.1, 외부 기본 경로 via 192.168.111.2. NAT는 inside local 10.10.20.10 → inside global 192.168.111.110, 목적지 1.1.1.1입니다. ICMP 콜론 뒤 값은 식별자이며 TCP/UDP 포트가 아닙니다.

조회가 끝나면 PC20에서 Ctrl+C로 시험을 중지합니다. 이 단계는 조회·시험만 수행하며 라우팅·NAT 설정을 다시 적용하지 않습니다. 이번 NAT 표는 변환 생성 근거이며 해당 연속 Ping의 전체 응답 출력은 별도 수집하지 않았습니다.

6. 설계 방향과 완료 범위

[검토] 사용자가 제안하고 이번 대화에서 적합하다고 검토한 방향은 VLAN10 개발/테스트, VLAN20 운영입니다. 현재 대역 10.10.10.0/24·10.10.20.0/24를 활용할 수 있습니다. 최종 단말 수·고정 주소·DHCP 정책·개발→운영 ACL은 아직 설계하지 않았습니다. 전체 호스트 IP 계획이 이미 확정된 것으로 해석하지 않습니다.

운영 스위치 두 대에 같은 VLAN20을 사용하면 같은 네트워크이며, 현재 VLAN 간 라우팅 성공이 영역 간 접근 제한을 뜻하지 않습니다.

이번 완료: DNS 설정·저장·재시작 유지(사용자 확인), 임시 경로 부재(사용자 확인), 현재 DHCP 임대·범위 관계, 이미지 이름(사용자 확인), VLAN 역방향 통신(사용자 확인), 제공 출력의 ARP·MAC·라우팅·NAT 대조.

남은 작업: 단말 배치·최종 주소 정책·접근 정책 구체화. HTTP/HTTPS 서비스, AWS/VPN, ACL/HA는 이번 검증 범위 밖입니다. 공식 상태·이력 갱신은 별도 요청된 최종 반영 단계에서 수행합니다.

7. 이번 진행 절차와 재질문 점검

실제 진행: 공통·프로젝트 규칙과 공유 인계 스킬 확인 → 최신 기록·현재 상태 복원 → DNS 실패 분석·설정·저장 → Linux 임시 경로 확인 → 관리 주소와 기록 충돌 분석 → 역방향 Ping → 이미지 이름 보완 → CORE ARP·경로 → ASW MAC → EDGE 경로·NAT → VLAN 역할 검토 → PC20 재시작 유지 확인 → 가이드·규칙 반영.

공통 재개 흐름은 상위 공통 작업 흐름으로 통합됐으며, 네트워크의 사용자 적용·실제 출력 검증 역할은 유지됐습니다. 이번 차이는 누락 증거를 보완하는 과정에서 확인 사유·범위 설명이 충분하지 않았던 점입니다.

확인 항목필요성 점검·개선
DNS·외부 IP미검증 DNS 진단에 필요. 외부 IP 성공 보고를 받은 뒤 같은 Ping은 다시 요구하지 않음.
저장·재시작 유지서로 다른 검증이라 필요. 처음부터 PC20만 재시작한다고 설명하고, 저장 완료 보고 후 재질문 중단.
Linux 임시 /32삭제 결과 미수집으로 조회 필요. 출력 없음 확인 후 종료.
.128과 DHCP과거 기록과 최신 출력 충돌로 확인 필요. dynamic·임대 IP·프로필로 현재 상태를 판단하고, Netplan은 원본 대조가 필요할 때만 추가. 주소 삭제·전체 호스트 계획 요구로 확대하지 않음.
이미지계열·기능은 재질문 불필요. 전체 이름만 누락된 문서 보완으로 설명. Template 화면 존재를 가정한 안내는 개선 필요.
역방향 Ping·ARP·MAC·NAT명시된 잔여 증거 보완 목적. 이미 검증된 동작을 전부 다시 확정해야 한다는 식의 필수 관문으로 만들지 않음.
명령 오류·출력량지원하지 않는 --pager 안내와 전체 Netplan 요청은 개선 필요. 기본 명령·현재 UUID·필요한 행만 안내.

앞으로의 절차: 기존 근거 확인 → 부족·충돌 식별 → 필수/조건부/문서 보완 구분 → 확인 이유·최소 명령·완료 기준 설명 → 사용자 실행 → 결과 판정 → 완료 항목 재사용.

이 절차는 프로젝트 상세 규칙의 「자료 확인과 가이드 고유 조건」에 반영했습니다. 가이드에만 두고 AI 행동 규칙과 분리하지 않습니다.
