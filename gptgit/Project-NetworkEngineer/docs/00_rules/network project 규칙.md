## $프로젝트 기본 규칙

- 사내망·클라우드 네트워크 구성과 웹서비스 동작 확인을 네트워크 엔지니어 실무 관점에서 수행한다. 구체적인 목표·제약은 [프로젝트 범위](../01_requirements/프로젝트%20범위.md)를 따른다.
- 표준적인 실무 기준과 실제 확인 가능한 정보를 우선한다. 전체 프로세스 설명은 실무 순서를 따르되, 실습의 구현 순서는 아래 학습 원칙에 맞춘다.
- 사용자 장비 적용·AI 설정안·검증 완료를 구분하며 실행 제약은 AGENTS를 따른다.

## $추론 및 사실 구분

확인되지 않은 환경·설정·장비 동작·원인을 사실로 단정하지 않는다. 추론은 표준 실무 필수 내용을 보완하거나 제공 정보로 판단해야 할 때만 사용한다.

| 표기 | 의미 |
| --- | --- |
| [확정] | 공식 문서·사용자 제공 정보·실제 확인 근거가 있음. 제공 출력과 사용자 성공 보고는 구분해 명시 |
| [일반적인 실무 기준] | 일반적으로 확립된 네트워크·IT 인프라 운영 방식 |
| [추론] | 제공 정보와 일반 기준을 바탕으로 한 판단 |
| [추론:확인필요] | 실제 환경·추가 정보 확인이 필요한 판단 |
| [검토] | 아직 결정하지 않은 비교·방향 |
| FIX | 기존 설계·판단을 수정한 내용 |
| [세부내용 확인] | 긴 세부 설명은 관련 문서·절로 연결 |

## $실무 중심 설명

- 개념만 나열하지 않고 목적·사전 확인·명령/설정·적용 순서·검증·예상 결과를 필요한 범위에서 설명한다.
- 대상 장비·OS·버전·설정 모드를 명시한다. IP·VLAN·포트·게이트웨이·라우팅·보안 값은 [실습 환경](../02_design/실습%20환경%20및%20주소.md)의 확인값을 사용하고 미확인 값은 예시/확인 필요로 표시한다.
- 영향 있는 변경은 기존 설정 보관·복구 방법을 필요한 범위에서 제시한다. 실행 실패 시 오류·증상을 근거로 범위를 좁히며 이미 받은 정보는 반복 요구하지 않는다.
- 구조는 적절한 다이어그램, 주소·VLAN·경로 대응은 표로 제시한다. 질문에 필요하지 않은 범위까지 확대하지 않는다.

## $프로젝트 진행 및 설계 원칙

전체 구조 이해 → 요구사항/현황 확인 → 설계 → 설정안 제시·사용자 적용 → 실제 출력·통신 검증 → 문제/개선 확인 → 필요 시 FIX·재구현·재검증 → 요청된 최종 반영·문서화.

전체 구조 이해와 학습 효과를 우선해 단계적으로 구현한다. 문제나 변경 필요가 있으면 기존 설계를 억지로 유지하지 않고 이유·영향·관련 설정을 설명해 수정한다. 설계 변경은 정상적인 절차다.

## $자료 확인과 가이드 고유 조건

- [문서 운영 및 재개](문서%20운영%20및%20재개.md)는 문서 책임, “작업기록 남겨줘”의 종료 반영, “작업기록 보고 다음 작업 진행해줘”의 조회 순서, 재확인 필요성·최소 출력·완료 처리의 기준이다. 동일 절차를 이 문서에 복사하지 않는다.
- 스킬 선택·원본은 [상위 AGENTS](../../../AGENTS.md), 공통 재개·PC 이동·기록 기준은 [공통 작업 흐름](../../../docs/common_workflow.md)을 따른다.
- 정확성에 필요한 근거는 생략하지 않는다. 동시에 기존 완료 사실을 재사용하고 추가 확인의 목적·필수 여부·종료 기준을 먼저 설명한다.
- 사용자 가이드는 확정 상태·검증 근거로 작성한다. 저장·구조 검사·결과 보고는 문서 운영 규칙에서 연결한 simple-user-guide를 따른다. 문서 작성과 실제 장비 적용을 구분한다.
