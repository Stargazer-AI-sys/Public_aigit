## $2 “작업기록 남겨줘” — 종료

1. 이번 대화의 제안·사용자 적용·제공 출력·사용자 성공 보고를 구분하고 최종 결과를 확정한다. 중간 설정·추정은 현재 상태로 올리지 않는다.
2. 요청 범위의 확정 결과를 분야별 원본에 반영한다. 환경 값은 환경 문서, 검증 근거는 검증 문서, 현재 단계·미확정·다음 작업은 진행상황에 기록한다. 작업기록 요청에는 그 작업의 공식 상태·근거 반영과 인계를 포함하되 다른 미완료 작업을 실행하지 않는다.
3. 기존 작업기록 맨 아래에 날짜별 항목을 추가한다. 아래 표의 항목을 간결하게 쓰고 상세 내용은 원본 링크로 연결한다. 기존 날짜별 기록은 보존한다.

| 인계 필수 항목 | 남길 내용 |
| --- | --- |
| 완료·정정 | 무엇을 완료했고 어떤 과거 판단을 대체하는가 |
| 근거·확인 수준 | 관련 문서/절, 제공 출력 또는 사용자 확인, 검증 한계 |
| 다음 작업 | 대상·목적·첫 행동·완료 기준·담당·필요한 입력 |
| 남은 결정·보류 | 재개 조건과 현재 작업을 막는지 여부 |
| 재질문 방지 | 이미 완료한 확인과 다시 확인할 조건 |
| 문서·Git | 실제 변경·검사·미실행 작업 |

4. 작업기록의 `latest-handoff` 고정 ID는 새 인계 바로 앞에 한 개만 둔다. 이전 인계의 같은 ID는 제거하되 본문 이력은 남긴다. 상단 최신 인계 링크는 이 ID를 사용해 날짜 변경에도 유지한다.
5. 수정 문서의 파일 링크·절 연결·중복 ID와 오래된 현재 상태 문구를 점검한다. 결과를 확인한 뒤 실제 검사 범위와 미검증을 보고한다. commit·push는 각각 별도 명시적 요청 없이는 실행하지 않는다.

## $3 “작업기록 보고 다음 작업 진행해줘” — 재개

1. README·적용 AGENTS·관련 기술 규칙을 확인한다. 같은 채팅에서 확인한 근거는 변경·누락·충돌이 있을 때만 재조회한다.
2. 작업기록의 [최신 인계](../04_records/작업%20기록.md#latest-handoff)부터 읽고 [진행상황의 다음 작업](../02_design/network%20project%20진행상황.md#next-work)과 대조한다. 날짜별 옛 “다음 작업”을 전부 읽거나 현재 할 일로 승계하지 않는다.
3. 인계에서 연결한 관련 범위·설계·환경·검증 절만 읽는다. 필요 시에만 과거 이력·가이드를 추가 확인한다. 전체 문서를 매번 순회하지 않는다.
4. 두 원본의 다음 작업이 다르면 최신 사용자 지시·근거 시점으로 대조하고 미해결 충돌을 알린다. 과거 PC 경로·설치·원격 미확인은 당시 정보로 구분한다.
5. 현재 상태·다음 첫 행동·미확인 입력을 짧게 보고한다. 범위가 정해진 설계·조회·분석은 계속하고 장비 적용은 사용자가 수행한다. 보류 재개·Git 동기화·새 설정 적용을 인계 존재만으로 허가받았다고 판단하지 않는다.

## $4 사용자 재확인 필요성 판단

1. 현재 채팅의 답변·출력, 진행상황·최신 인계의 관련 근거부터 확인한다. 역할·이미지 계열·실행 버전·전체 이름, 설정 저장·재시작 유지는 별도 항목이다.
2. 기존 근거가 충분하고 변경·증상·충돌이 없으면 재사용한다. 새 채팅·날짜 경과·과거 할 일만을 이유로 완료 검사를 반복하지 않는다.
3. 다음 작업에 필수인 값 누락, 기록과 최신 출력 충돌, 환경 변경·장애, 현재 변경 영향 검증, 요청된 증거 보완이 있을 때만 추가 요청한다. 단순 문서 보완을 실습의 필수 관문으로 만들지 않는다.
4. 요청 시 **기존 사실 → 부족/충돌 근거 → 목적 → 필수/조건부/문서 보완 → 최소 명령·보낼 부분 → 완료 기준**을 짧게 설명한다.
5. 답변에 의존하는 작업만 대기하고 독립적인 확인은 계속한다. 전체 출력보다 필요한 NIC·프로필·행부터 요청한다. 조회 결과로 판단할 수 있으면 설정 변경·종료·재부팅을 먼저 요구하지 않는다.
6. 같은 판단의 조회는 적절히 묶고 추가 명령은 앞선 결과가 부족할 때만 안내한다. 지원 불명 옵션·화면 항목은 도움말·공식 자료로 확인하거나 기본 조회를 사용한다.
7. 과거 사용자 보고와 현재 출력이 다르면 둘의 시점·의미를 함께 남긴다. 주소 두 개 또는 DHCP 범위 포함만으로 IP 충돌을 단정하지 않는다. 관리망 DHCP와 실습 VLAN DHCP, 검증용 주소와 최종 호스트 계획을 구분한다.
8. 종료 기준을 충족하면 완료 처리한다. 사용자 성공 보고를 받아들이고 추가 원시 출력이 꼭 필요한 별도 이유가 없으면 재요청하지 않는다. 종료 시 공식 근거와 인계에 연결해 다음 채팅에서도 재사용한다.

## $5 카테고리·가이드·문서 분리

- `$ → % → ^`는 상위·하위·세부 계층이다. 많은 항목은 `$1`, `%1`, `^1`처럼 번호를 붙인다. `%`와 `^` 번호는 각 상위 항목 안에서 독립적으로 시작하며 중요도·우선순위가 아니다.
- Markdown `#` 제목 계층과 카테고리는 별개다. 예: `## $2 현재 환경` → `### %1 Linux` → `#### ^1 관리 NIC`. 일반 목록에는 강제하지 않으며 필요 없는 세부 계층은 만들지 않는다.
- 기존 번호 의미를 바꿀 때 연결 문서를 확인한다. 기존 진행상황 `$1~$9`는 이동 안내를 남겨 과거 참조의 진입점을 유지한다. 빈 옛 세부 절을 모두 복제하지 않는다.
- 문서 분리는 줄 수만으로 하지 않는다. 서로 다른 책임이 섞이거나 같은 상세 상태를 여러 곳에서 갱신하게 될 때 나누고, 원본 한 곳과 필요한 연결만 남긴다. 날짜별 작업기록의 분량이 감당 가능한 동안에는 월별 파일로 미리 분할하지 않는다.
- 사용자 가이드 기본 위치는 프로젝트 `guide_docs/`다. Library 식별 경로를 로컬 실행 경로로 쓰지 않는다. 기존 가이드의 식별자·이력은 유지한다.
- 명시적 가이드 작성·수정에는 [simple-user-guide 공유 원본](../../../skills/simple-user-guide/SKILL.md)을 적용한다. 확정 근거를 재사용하고 해당 HTML의 구조 점검·결과 보고를 수행한다. MD 분리만 한 작업에 HTML 검사를 강제하지 않는다.
