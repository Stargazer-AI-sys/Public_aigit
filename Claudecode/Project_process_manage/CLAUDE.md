# Project_process_manage 지침

상위 `Claudecode/CLAUDE.md`의 공통 규칙에 더해 이 프로젝트에만 적용한다.

## 목적 (2026-10-29 시작, 실험)
- 다른 프로젝트의 AI 작업 프로세스(Claude Code·Codex 등 LLM이 설계했거나 따르는 절차)를 점검한다.
- 코드 품질이 아니라 **사용자가 결정해야 하는 지점의 간소화**와 **비용**을 본다.

## 시작할 때
- `WORK_LOG.md`를 먼저 읽고 "현재 상태"와 "다음 단계"부터 이어간다.
- 사용자가 "작업기록"이라고 하면 이 폴더의 `WORK_LOG.md`를 뜻한다(다른 프로젝트의 같은 이름 문서와 구분).
- `WORK_LOG.md`는 작업 중 수시로 갱신하지 않는다. 사용자가 작업을 마칠 때 요청하면 한 번에 정리한다.

## 점검 대상과 범위
- 점검 대상 폴더는 **읽기만 한다**(예: `gptgit/…`, `Claudecode/Project_Refactor/`). 수정안은 이 폴더의 보고서로만 남긴다.
- 점검 결과는 `reports/<날짜>_<대상>.md`에 둔다.
- 대상에서 비밀값이 들어 있을 수 있는 파일(키, 자격 증명, `data/publish/prompt.txt`의 절대 경로 등)은 값을 옮겨 적지 않고 위치만 적는다.

## 점검 기준
1. **사용자 결정 지점:** 어디서 사용자 확인·승인·붙여 넣기가 필요한가. 꼭 필요한 것과 미리 정해 두면 없앨 수 있는 것을 나눈다.
2. **비용:** 유료 API 호출, 모델 선택, 반복 실행·재시도, 매번 읽는 문서의 양(토큰).
3. **지침 충돌:** 같은 대상에 대한 `AGENTS.md`(Codex)와 `CLAUDE.md`(Claude)의 규칙이 서로 다르거나 한쪽에만 있는 것.
4. **인계 구조:** LLM·PC·사람 사이에 무엇이 어떤 파일로 넘어가는가. 끊기거나 모호한 곳.
- 각 항목은 근거(파일 경로·줄)와 함께 "확인 / 추정 / 확인 필요"로 구분한다.

## 설명 방식
- 사용자는 코딩 지식이 낮다. 쉬운 말로 설명하고 전문 용어에는 짧은 풀이를 붙인다.

## Git
- commit과 push는 사용자가 요청하면 Claude가 한다. 요청 없이 실행하지 않는다.
