### 저장소 구조 (`s1-tree`)

- 단락: `자료와 설정을 저장소 두 개로 나눴습니다. 자료는 에이전트가 쌓고, 설정은 제가 검토한 것만 서버로 내려갑니다.`

  ```
  llmwiki/            ← 자료 저장소
  ├─ raw/             수집 담당이 저장한 원문
  └─ wiki/            정리 담당만 쓰는 위키 페이지 (검색 대상)
  agent-config/       ← 봇 설정 저장소
  ├─ souls/           에이전트별 정체성·경계·안전 규칙
  ├─ skills/          raw-save, wiki-ingest, wiki-lint-weekly, wiki-search, config-propose
  └─ common/          형식 규약 (서버에는 배치하지 않음)
  ```
  - 굵게: `llmwiki/`, `agent-config/`, `raw/`, `wiki/`, `souls/`, `skills/`, `common/`
  - 흐린 주석: `←` 뒤 설명과 각 줄의 설명

### 프로세스 (`s1-flow`)

- 순서도(SVG, `components/case/flow-side-llmwiki.tsx`) 칸 구성
  1. `Slack` (사용자 요청: URL 전달·질문)
  2. `Hermes 컨테이너` 안에 `수집`·`리서치`·`정리` 세 칸
  3. `수집` → `llmwiki raw/` 커밋, `정리` → `llmwiki wiki/` 커밋(llmwiki MCP 사용)
  4. `리서치`·`정리` → `qmd 검색`(점선, 읽기)
  5. 저장소 → `서버 자동 push(10분)` → `GitHub`(강조 칸 `.me`: 에이전트 밖에서 처리하는 부분)
- 캡션: `에이전트는 서버 안에서 커밋까지만 합니다. GitHub에 올리는 일은 에이전트가 볼 수 없는 서버 쪽 작업이 맡습니다.`
- 순서 카드
  - `자료 보내기` / `Slack 수집 채널에 URL을 보내면 수집 담당이 원문을 raw로 저장하고 커밋합니다.`
  - `위키로 정리` / `정리 담당이 새 raw를 읽고 위키 페이지를 만들거나 고친 뒤 커밋합니다.`
  - `GitHub 반영` / `서버가 10분마다 새 커밋을 GitHub에 올립니다.`
  - `검색 후 답변`(강조) / `질문을 받으면 qmd로 위키를 검색하고, 찾은 문서를 직접 열어 근거와 함께 답합니다.`

### 발생한 문제 (`s1-issue`)

1. 제목: `봇 두 개가 갑자기 답하지 않았습니다`
   - 근거(확인): `서버 로그에 토큰 만료 오류(token_expired)가 재시작 전까지 664건 반복됐습니다.` (§2 Slack 장애)
   - 원인: `Slack 앱 토큰이 12시간마다 만료되는 회전형이었고, 회전은 한 번 켜면 끌 수 없었습니다.`
   - 조치: `회전 없는 앱을 새로 만들어 토큰을 바꿨고, 이후 연결 오류는 0건이었습니다.`
   - 영향: `어느 봇에도 토큰 회전을 켜지 않는다는 운영 규칙을 남겼습니다.`
2. 제목: `한국어로 검색하면 문서를 찾지 못했습니다`
   - 근거(확인): `위키 기본 검색에서 “샌드박스”는 0건이고 “샌드박스가”처럼 조사가 붙은 원문 형태만 찾았습니다.` (§2 로컬 위키 시험)
   - 원인: `위키 기본 검색 색인이 영어 기준으로 단어를 나눴습니다.`
   - 조치: `한국어 임베딩 모델을 쓰는 qmd를 붙여 키워드 검색과 의미 검색을 함께 쓰게 했습니다. 시험 질의 12개 중 키워드 검색은 11개에서 정답 문서를 찾았고, 의미 검색은 12개 모두 정답을 상위 3개 안에 넣었습니다.`
   - 한계: `위키 문서가 4개뿐인 상태의 시험이라 검색 순위 품질은 아직 판단할 수 없습니다.`
3. 제목: `검색 모델이 서버 메모리를 밀어냈습니다`
   - 근거(확인): `2GB 서버에서 첫 임베딩 시험 중 스왑이 316MB에서 586MB로 늘고, 에이전트 컨테이너 메모리가 밀려났습니다.` (§2 qmd 서버 시험)
   - 원인: `임베딩 모델을 처음 올릴 때 메모리를 한 번에 많이 썼습니다.`
   - 조치: `중단 기준을 둔 별도 컨테이너에서 두 모델을 비교하고, 검색 서버는 700MB 한도로 상시 실행, 색인은 새벽에 1GB 일회용 컨테이너로 돌리며 여유 메모리가 900MB 미만이면 건너뛰게 했습니다.`
4. 제목: `에이전트가 기준 브랜치를 직접 바꿀 수 있었습니다`
   - 근거(확인): `저장소 키는 브랜치를 제한할 수 없고, 비공개 저장소에서는 GitHub 브랜치 보호 규칙도 적용되지 않았습니다.` (§1 2026-11-17, §2 GitHub ruleset)
   - 원인: `처음 계획은 에이전트 컨테이너에 저장소 키를 연결하는 것이었습니다.`
   - 조치: `키를 컨테이너 밖에 두고 서버 계정이 push하게 바꿨습니다. 컨테이너 안에서 push가 실패하는 것까지 확인했습니다.`
