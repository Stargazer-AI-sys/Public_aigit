# 요미코 위키 읽기(qmd) 연결 계획서 (초안)

> 작성 2026-11-18. **제안 단계이며 아직 서버에 적용하지 않았다.** 사용자 승인 전에는 서버를 바꾸지 않는다.
> 표시: **[확인]** 직접 실행·읽어서 확인한 사실, **[제안]** 이 계획의 설계, **[미확인]** 가정이거나 아직 시험하지 않은 것.
> 서버 IP, 키 파일명, 채널 ID는 적지 않는다. 명령의 `<...>`는 자기 값으로 바꾸는 자리다.

## 1. 목표와 범위
- 요미코(`yomiko` 프로필)가 `llmwiki` 위키(`wiki/`)를 **읽기 전용**으로 검색해 답에 쓰게 한다. 위키 쓰기는 카구야만 한다는 기존 원칙을 지킨다.
- 이번 범위: 요미코 한 프로필, 컬렉션은 `wiki/` 하나, 검색 방식은 `lex`/`vec`만. 카구야·애니 연결, `raw/` 검색, 재순위·쿼리 확장은 범위 밖이다.
- 성공 기준(§8)을 통과하지 못하면 §9 대안으로 옮긴다(사용자 요청: "qmd로 올려 보고 문제가 생기면 옮기는 것을 고려").

## 2. 근거 (2026-11-17~18 시험, 상세는 `WORK_LOG.md` §2)
- **[확인]** 임베딩 모델은 KURE-v1 Q8_0(`mykor/KURE-v1-gguf`, MIT)으로 정했다(§1 결정). warm `vec` 쿼리 약 0.33초, 색인 4청크 31~51초.
- **[확인]** 메모리(한국어 위키 4문서 기준): 색인은 한도 1GB 필요(700MB는 OOM), 서빙은 한도 700MB·병렬도 1에서 anon 약 410MB, 유휴 후 첫 쿼리 피크 약 545MB.
- **[확인]** `lex`는 정확한 용어에 강하고 조사가 붙은 말은 놓칠 수 있다. `vec`는 의미·조사 변형에 강하고 정확한 용어 1순위를 놓칠 수 있다. 융합(`lex`+`vec`, `rerank:false`)은 정답 1순위였다.
- **[확인]** 재순위·확장 모델 파일이 없고 네트워크가 막힌 qmd에서 `rerank` 미지정 호출과 MCP 평문 `query`는 **120초 멈춤**(오류·OOM 없음). REST `/query`의 평문 `query`는 즉시 400.
- **[확인]** 서버 현재 상태(2026-11-18): `hermes`(`unless-stopped`, 메모리 한도 없음, 기본 `bridge` 네트워크), `llmwiki-api`(네트워크 없음, 300MB 한도). 사용자 정의 Docker 네트워크는 없다. 메모리 available 약 1.1GB(스왑 약 586MB 사용 중), 위키 `.md` 파일 8개(wiki 4, raw 4).
- **[확인]** 호스트 cron(`hermes-git-sync.sh`)이 10분마다 `~/llmwiki`를 fast-forward로 pull하고 push한다. 위키 변경은 이 경로로 서버에 들어온다.

## 3. 목표 구조 [제안]

```
요미코(hermes 컨테이너) ──(내부 네트워크 qmd-net)──▶ qmd 서빙 컨테이너  ◀── 위키(읽기 전용)
   wiki-search 스킬                                   모델: KURE-v1만          ~/llmwiki/wiki
   (REST /query, rerank:false 고정)                   인터넷 없음, 700MB
```

| 구성요소 | 설계 |
|---|---|
| qmd 서빙 컨테이너 `qmd` | `node:22-slim` + `@tobilu/qmd`(버전 고정), 한도 700MB·스왑 없음, 병렬도 1, `restart unless-stopped`, 모델은 KURE-v1 하나만 둔다(재순위·확장 파일은 받지 않는다) |
| 네트워크 `qmd-net` | Docker `--internal`(외부 통신 불가) 네트워크. `qmd`와 `hermes`만 연결. `hermes`는 기존 `bridge`도 유지해 Slack·웹 접근이 그대로다 |
| 위키 마운트 | `~/llmwiki/wiki`를 읽기 전용으로 `/wiki`에 연결 |
| 색인 컨테이너 | 단발 실행, 한도 1GB, 색인 때만 네트워크 없이 실행(모델은 설치 단계에서 미리 받는다) |
| 요미코 스킬 `wiki-search` | `agent-config/skills/wiki-search/`에 작성 → 기존 배포 방식(main 병합 → 서버 pull → 프로필별 복사) |

## 4. 안전장치 (겹겹이) [제안]
1. **서버 쪽:** 인터넷 차단, 재순위·확장 모델 파일 미배치, 메모리 한도. 평문 `query`나 `rerank` 기본값이 와도 OOM이 아니라 멈추고, 한도 초과 시 qmd 컨테이너만 재시작된다.
2. **스크립트 쪽:** REST `/query`만 호출, `searches`(`lex`/`vec`/`hyde`)만 보내고 `rerank:false` 고정, 요청 타임아웃 20초(서버 멈춤 120초보다 짧게), 응답 개수 상한, 호스트는 환경변수로 고정된 `qmd:8181`만 허용.
3. **지침 쪽:** SOUL "하는 일"에 한 줄, 스킬에 사용법(§6). 규칙은 최후의 방어로만 본다.
4. **읽기 전용:** qmd는 위키를 읽기 전용으로 마운트하고 쓰기 도구가 없다. 단, `hermes` 컨테이너는 `~/llmwiki`가 쓰기 가능으로 연결돼 있어(§2) 요미코가 파일로 위키를 쓰는 것은 기존대로 SOUL 규칙이 막고 있다. 이 계획이 새로 늘리는 위험은 아니다.
5. **한계:** 같은 `hermes` 컨테이너 하나가 세 프로필을 처리하므로 `qmd-net` 접근을 요미코에게만 줄 수 없다(애니·카구야도 호출 가능). 읽기 전용이라 위험은 낮다고 본다.

## 5. 단계별 계획
각 단계는 서버를 바꾸므로 **착수 전에 사용자 승인**을 받는다. 서버에 영향을 주는 단계는 되돌리는 방법을 함께 둔다.

**단계 0 — 사용자 결정(§7)**: 서버 증설 여부, 시작 시점, 컬렉션 범위.

**단계 1 — qmd 설치와 색인(`hermes`에 영향 없음)**
- 작업: `/srv/qmd/{app,data}` 생성, `node:22-slim` 가져오기, `@tobilu/qmd`를 버전 고정으로 설치(설치 중 컨테이너 한도 700MB), KURE-v1 Q8_0 모델 내려받기(약 635MB, 이때만 인터넷 사용), 컬렉션 `wiki` 등록, 색인(한도 1GB).
- 확인: `qmd status`(문서 4개, 벡터 생성), 모델 파일 크기·체크섬 기록, 색인 중 호스트 available·스왑(중단 기준: available 300MB 미만 또는 호스트 스왑 1.2GB 초과, 시험 때와 같게).
- 되돌리기: `/srv/qmd` 삭제.

**단계 2 — 서빙 컨테이너와 내부 네트워크(`hermes`에 아직 연결 안 함)**
- 작업: `docker network create --internal qmd-net`, 컨테이너 `qmd`를 `qmd-net`에서만 실행(`--network none`이 아니라 `qmd-net`), 환경변수 `QMD_ALLOWED_HOSTS`에 서비스 이름 `qmd` 포함 **[미확인: 호스트 검사 설정값]**.
- 확인: 임시 컨테이너를 `qmd-net`에 붙여 `/health`와 `/query`(`lex`·`vec`·융합) 호출, 메모리 기록. 인터넷 차단 확인(임시 컨테이너에서 외부 접속 실패).
- 되돌리기: `docker rm -f qmd`, `docker network rm qmd-net`.

**단계 3 — `hermes`를 `qmd-net`에 연결(운영 중인 컨테이너에 영향)**
- 작업: `docker network connect qmd-net hermes`(재시작 없이 연결 **[미확인: 실행 중 컨테이너에 연결되는지, DNS 이름이 풀리는지]**).
- 확인: `hermes` 안에서 Python으로 `http://qmd:8181/health` 호출, Slack 세 봇 연결 유지(로그), 인터넷 접근 유지(기존 웹 검색 동작).
- 되돌리기: `docker network disconnect qmd-net hermes`.

**단계 4 — 요미코 스킬(PC 작업)**
- 작업: `agent-config/skills/wiki-search/`(SKILL.md + `scripts/qmd_search.py`, 파이썬 표준 라이브러리만) 작성 → 시험 → main 병합 → 서버 `~/agent-config` pull → `~/.hermes/profiles/yomiko/skills/<분류>/wiki-search/`에 복사. 필요하면 `yomiko.SOUL.md` "하는 일"에 한 줄.
- 확인: `hermes -p yomiko skills list`에 `enabled`, Slack `#research`에서 요미코에게 위키 관련 질문 3~5개(한국어·영어), 답에 위키 페이지 경로가 인용되는지, 응답 시간.
- 되돌리기: 프로필 폴더의 스킬 삭제.

**단계 5 — 색인 갱신 자동화**
- 문제: 카구야가 위키를 고치면 `llmwiki`가 바뀌지만 qmd 색인은 자동으로 갱신되지 않는다. 호스트 cron(`hermes-git-sync.sh`)은 docker를 쓸 수 없는 `hermes` 계정(uid 10000)으로 돈다 **[확인: 스크립트 내용]**.
- 제안: root cron 스크립트가 10~15분마다 `~/llmwiki`의 `wiki/` 변경 여부를 확인하고(마지막 색인 시점의 HEAD 해시와 비교), 바뀌었을 때만 ① `qmd` 서빙 컨테이너 중지 ② 색인 컨테이너(1GB) 실행 ③ 서빙 컨테이너 시작. `flock`으로 중복 실행 방지, 호스트 available가 낮으면 건너뛰고 기록. 서빙을 멈추는 이유는 색인(1GB)과 서빙(700MB)이 동시에 떠 있으면 `hermes`가 스왑으로 밀리기 때문이다(시험에서 확인한 부작용).
- 확인: 카구야가 위키를 고친 뒤(또는 시험용 변경) 15분 안에 새 내용이 검색되는지, 색인 중 서빙 중단 시간, `hermes` 영향. 서빙 중단 없이 색인 DB 갱신이 반영되는지는 **[미확인]**이라 먼저 한 번 시험하고 중단 방식 여부를 정한다.
- 되돌리기: cron 파일 삭제.

**단계 6 — 관찰**
- 2~3일 동안 §8 기준을 점검한다. 점검 명령 예: `docker stats --no-stream`, `docker inspect qmd -f '{{.RestartCount}} {{.State.OOMKilled}}'`, `free -m`, `swapon --show`, `tail /var/lib/hermes-sync/sync.log`.

## 6. 스킬 초안 요약 [제안]
- 이름 `wiki-search`, 사용 시점: 위키에 이미 정리된 내용을 찾아 답할 때(요미코).
- 호출: `qmd_search.py --lex "<명사 어간>" --vec "<문장형 질의>" [--limit 5]`. 둘 다 있으면 융합, 하나만 있으면 단독.
- 스크립트가 보내는 본문: `{"searches":[...], "rerank":false, "limit":N}` 고정. 평문 `query`를 만들 수 없게 인자 자체를 받지 않는다.
- 사용법(스킬 본문): `lex`는 띄어쓰기·조사 없는 핵심 명사(예: "옵시디언"), 정확한 용어(고유명사·영어)는 `lex`를 함께, 의미 질문은 `vec`. 결과가 비면 어간·동의어로 `lex`를 바꿔 다시 시도하고, 그래도 없으면 "위키에 없음"으로 답한다.
- 출력: 위키 상대 경로, 제목, 점수, 요약 조각. 전문이 필요하면 요미코가 경로로 파일을 읽는다.
- 실패 처리: 연결 실패·타임아웃(20초)이면 오류 문구와 함께 종료 코드 비정상으로 끝내고, 요미코는 "검색 서버 응답 없음"을 사용자에게 알리거나 파일을 직접 읽는 대안을 쓴다.
- 기존 결정과의 차이: 2026-11-16의 "qmd 플러그인 스킬을 그대로 쓴다"와 다르다. 플러그인 스킬이 평문 `query`를 권하는지는 확인하지 않았다 **[미확인]**.

## 7. 사용자 결정
**2026-11-18 사용자 답변:** (1) 증설은 아직 하지 않는다(2GB 서버로 진행). (2) 컬렉션은 `wiki/`의 정리된 내용만. (3) 카구야도 연결한다(요미코와 같은 스킬을 쓰는 것으로 해석, 카구야 연결 방식은 단계 4에서 확인). (4) 착수 시점은 지금 해도 된다. 아래는 답변 전 원문이다.

1. **서버 증설:** $24(4GB) 이상으로 올릴지. 계산상 2GB 서버에서 `hermes`(활성 시 약 500MB) + qmd 서빙 피크(anon 약 545MB)가 동시에 있으면 available이 300MB 안팎까지 내려갈 수 있다(추정, 시험 중 `hermes`는 스왑으로 밀려 있었음). **권장: 증설 후 단계 1 시작**, 증설하지 않으면 §8 점검 기준을 더 엄격히 적용하고 문제 시 §9로 이동.
2. **컬렉션 범위:** `wiki/`만(권장) 또는 `raw/` 포함. 요미코 SOUL은 위키 읽기를 전제로 하므로 `wiki/`만으로 시작한다.
3. **카구야 연결 여부:** 이번에는 제외 권장(중복 확인은 llmwiki `search`). 요미코 시험 통과 뒤 다시 결정.
4. **착수 시점:** 단계 3(운영 컨테이너 네트워크 변경)부터는 Slack 사용이 적은 시간에 한다.

## 8. 성공 기준과 중단 기준
- **성공(관찰 2~3일):**
  - 한국어·영어 질의 12개 이상에서 정답 문서가 top-3 안에 있다(문서가 늘었으면 새 질의로 다시 만든다).
  - `qmd` 컨테이너 재시작 0회, OOM 0회.
  - 호스트 스왑이 증설 전 기준(약 586MB)에서 더 늘지 않는다. `hermes` 응답 시간이 시험 전 수준(Slack 응답 3~6초대)을 유지한다.
  - 위키 변경이 15분 안에 검색 결과에 반영된다.
- **중단 후 대안 이동:** 호스트 available 300MB 미만이 반복되거나, 스왑이 1.2GB를 넘거나, `hermes` 응답이 눈에 띄게 느려지거나, 색인 갱신이 안정적으로 안 되면 qmd를 멈추고 §9로 간다.

## 9. 대안 (사용자 지침: 문제가 생기면 옮기는 것을 고려)
1. 위키가 작은 동안 요미코가 `~/llmwiki/wiki/*.md`를 파일로 직접 읽는다(추가 구성 없음, 위키가 커지면 비효율).
2. llmwiki의 `search`만 읽기 전용으로 노출하는 얇은 래퍼. llmwiki MCP는 쓰기·삭제 도구를 함께 노출하므로 그대로 연결하지 않는다.
3. qmd를 증설한 서버에서 다시 시도하거나, 임베딩을 원격 OpenAI 호환 서버로 돌린다(위키 내용이 외부로 나가므로 사용자 승인 필요).

## 10. 위험과 미확인 정리
| 항목 | 상태 |
|---|---|
| `docker network connect`가 실행 중인 `hermes`에 재시작 없이 되는지, `qmd` 이름 해석, `QMD_ALLOWED_HOSTS` 설정 | 미확인 (단계 2·3에서 확인) |
